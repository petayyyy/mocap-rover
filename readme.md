# Арена локализации — Gazebo Harmonic

> Текущая доработка локализации: [статус и ограничения](docs/localization_plan/STATUS.md),
> [команды запуска/остановки](docs/localization_plan/operator_runbook_sim.md).
> Обученные веса, калибровки и записи находятся в `artifacts/post-reboot/`.
> Полная приёмка S15 пока не пройдена.

Мир `worlds/mocap_arena.sdf`: полигон 12×12 м, прозрачный потолок на Z=3 м,
шесть потолочных камер и два независимо управляемых ровера. Начало координат
в углу пола; X,Y ∈ [0,12], Z направлена вверх. Модели автономные, Fuel и ROS
для запуска не нужны. Требуется Gazebo Harmonic (Sim 8).

## Запуск и варианты внешности

```bash
./scripts/run.sh
```

Арена приближена к фотографии по материалам и освещению: чёрный пол со швами
панелей и потёртостями, низкие тёмные борта с бирюзово-розовой лентой,
девять цветных потолочных прожекторов и мягкий общий свет. Верхние стены
прозрачные для удобства обзора. Внутренние борта занимают 16 см вдоль каждой
границы. Дым, зрители, повреждения и точная геометрия боевых роботов не моделируются.

Ровер с AprilTag — приглушённый графитовый. Ровер без метки имеет пять вариантов
материалов; размеры и физика одинаковы для сравнения детекции:

| `--style` | Внешность |
|---|---|
| `steel` | Стальной, металлические панели — по умолчанию |
| `dark` | Тёмный матовый корпус и тёмная надстройка |
| `light` | Светло-серый корпус, серая надстройка |
| `sand` | Приглушённый песочный корпус |
| `two-tone` | Тёмный корпус, светлая надстройка |

Чтобы сменить вариант, закройте текущее окно Gazebo, создайте мир и запустите снова:

```bash
python3 scripts/generate_world.py --style dark --seed 42
./scripts/run.sh
```

Параметры без указания принимают значения по умолчанию, а не предыдущие значения.
Генератор изменяет файлы на диске; уже запущенный мир от этого не обновляется.
Сохраняйте одинаковые `--seed` и пределы погрешностей для сравнения цветов.
В мире всегда два ровера — варианты без метки выбираются по одному.

Управление светом:

```bash
# Цветное освещение; множитель яркости 0..4, по умолчанию 1
python3 scripts/generate_world.py --style light --lighting colored --light-intensity 1.3
# Нейтральное освещение для контрольного эксперимента
python3 scripts/generate_world.py --style light --lighting neutral
```

Параметры сцены сохраняются в `config/scenario.json`. Отдельные наборы можно
создавать без перезаписи основного мира:

```bash
python3 scripts/generate_world.py --style sand --seed 7 --output-dir /tmp/arena-sand
# Запуск отдельного мира с теми же исправлениями графического окружения:
MOCAP_WORLD=/tmp/arena-sand/worlds/mocap_arena.sdf ./scripts/run.sh
```

## Погрешности установки камер

Номинальные точки, все на Z=2.9 м:

| Камера | X, м | Y, м |
|---|---:|---:|
| camera_1 | 3 | 2 |
| camera_2 | 9 | 2 |
| camera_3 | 3 | 6 |
| camera_4 | 9 | 6 |
| camera_5 | 3 | 10 |
| camera_6 | 9 | 10 |

По умолчанию генератор независимо выбирает равномерные ошибки каждой камеры:

- смещение по X, Y и Z: **±3 см на каждую ось**;
- вращение вокруг мировой X (`roll`): **±0.5°**;
- вращение вокруг мировой Y (`pitch`): **±5°**;
- вращение вокруг мировой Z (`yaw`): **±0.5°**.

Это принятое распределение ошибок монтажа: основная неопределённость — наклон
вокруг Y. Если ±5° нужны по другой оси, поменяйте соответствующие параметры.
Поворот вокруг Z меняет направление длинной стороны изображения.

```bash
python3 scripts/generate_world.py --style steel --seed 42 \
  --position-cm 3 --roll-deg 0.5 --pitch-deg 5 --yaw-deg 0.5

# Неопределённость наклона по обеим горизонтальным осям
python3 scripts/generate_world.py --roll-deg 5 --pitch-deg 5 --yaw-deg 0.5

# Другой монтаж, воспроизводимый по seed
python3 scripts/generate_world.py --seed 123

# Идеальные положения для сравнения
python3 scripts/generate_world.py --ideal-cameras
```

Ошибки постоянны в течение запуска, а не меняются на каждом кадре. Один seed
даёт одинаковые ошибки независимо от выбранного материала ровера и света.
Допускаются смещения до 5 см на ось и угловые пределы до 15°.
Пиксельный шум, дисторсия и дрожание камер в эту модель не включены.

### Калибровка и эталон

- **`config/cameras.json`** — номинальные, некалиброванные положения.
- **`config/cameras_ground_truth.json`** — реальные положения камер в симуляции,
  фактические матрицы и ошибки монтажа. Используйте только для оценки результата.
- **`config/scenario.json`** — seed, пределы ошибок, стиль, свет и отчёт покрытия.

Оба файла камер содержат K, D, `position_world` и `R_world_optical`.
Преобразование: `p_world = R_world_optical @ p_optical + position_world`.
В идеале оптические оси: вправо +X мира, вниз −Y мира, вперёд −Z мира.
Фактическое вращение:

```text
R_actual = Rz(yaw) Ry(pitch) Rx(roll) R_nominal
```

При наклонённых камерах простой пересчёт пикселей по высоте уже неверен:
нужно пересечение луча с плоскостью. Для этого есть инструмент:

```bash
# Оценка по номинальным положениям (будет содержать ошибку установки)
python3 scripts/project_pixel.py camera_1 800 600 --height 0.3654

# Контроль по эталонным положениям
python3 scripts/project_pixel.py camera_1 800 600 --height 0.3654 \
  --calibration config/cameras_ground_truth.json
```

После собственной калибровки передайте JSON такого же формата через
`--calibration`. Инструмент работает с pinhole-камерой без дисторсии; для реальной
камеры предварительно исправьте дисторсию пикселя. Сам алгоритм калибровки и
калибровочная мишень здесь не реализованы. Ground truth не следует подставлять
в алгоритм вместо результата калибровки.

### Изображения и покрытие

RGB 1440×1080, 30 Гц симуляционного времени, без дисторсии. Топики:

- `/cameras/camera_N/image` — `gz.msgs.Image`;
- `/cameras/camera_N/camera_info` — `gz.msgs.CameraInfo`.

В GUI добавьте **Image Display** и выберите нужный топик. K в JSON номинальная;
для обработки кадров используйте публикуемый CameraInfo, который содержит
внутренние параметры, а не результат внешней калибровки.

В идеальном монтаже поле зрения на полу 8.2×6.15 м (HFOV ≈109.5°),
на Z=0.5 м — 6.79×5.09 м. Увеличенный угол сохраняет запас на высоту ровера.
С погрешностями форма и перекрытие областей меняются. Генератор проверяет
геометрическое покрытие сеткой 10 см на Z=0, 0.3654 и 0.5 м и выводит число
непокрытых точек. Это дискретная проверка, без учёта заслонения бортами и роверами;
нулевое число не гарантирует видимость каждого объекта целиком.

## Лидар и мир с лидаром

Основной мир `worlds/mocap_arena.sdf` лидара не содержит. Мир
`worlds/mocap_arena_l2.sdf` добавляет потолочный лидар в центре арены на
высоте 2.75 м, направленный вниз, и используется во всех прогонах локализации.

Лидар в нём — **RoboSense Airy**, характеристики взяты из руководства
производителя:

| | значение |
|---|---|
| частота кадров | 10 Гц (600 об/мин) |
| каналов | 96 |
| угловое разрешение Г/В | 0.4° / 0.947° |
| поле зрения | 360° × 90° (полусфера) |
| лучей за оборот | 85 500 |
| точек в секунду | 855 000 |
| дальность | 60 м (30 м при 10% отражении) |
| точность | 1.5 см (1σ) |

Измерено в симуляторе: интервал между сканами 100.0 мс, 85 500 возвратов,
127 и 362 точки на роверах на дальностях 5 и 3 м.

Сменить модель сенсора:

```bash
python3 scripts/set_world_lidar.py worlds/mocap_arena_l2.sdf --profile airy --rename
```

Профили (`airy`, `l2`) несут опубликованные характеристики сенсора, а не
настроечные коэффициенты, чтобы мир не мог разойтись с даташитом.
`--dry-run` покажет изменения не записывая их.

**После смены сенсора фон обязательно перезаписать.** Воксельная карта
пустой арены снималась под прежний рисунок луча и новый не описывает: при
переходе с L2 на Airy она вырастает с 968 до 2542 вокселей, и на старой карте
около 1600 вокселей статики арены читались бы как движущийся объект.

```bash
python3 scripts/record_lidar_background.py --scans 40
```

Скрипт сам убирает роверы из мира и поднимает свою копию симуляции, поэтому
запускать его нужно при остановленной арене. Результат — `config/lidar_background.json`.

## Роверы, метка и управление

`tag_rover`: корпус 0.72×0.52 м, старт (3,2), AprilTag **36h11 ID 0 сверху и ID 1 снизу**.
`yolo_rover`: корпус 0.9×0.52 м, старт (9,6), надстройка, капот и бронепанель,
без метки. Оба четырёхколёсные, направление вперёд — +X.

Чёрный внешний квадрат AprilTag: **0.40 м** (`tag_size`), белая подложка — 0.50 м.
Центр поверхности относительно `base_link`: (0,0,0.2254) м; в покое Z≈0.3654 м.
Нормаль метки +Z; рисунок сверху при +X вправо и +Y вверх соответствует
[официальному PNG AprilRobotics](https://github.com/AprilRobotics/apriltag-imgs/blob/master/tag36h11/tag36_11_00000.png).
Оригинал в `assets/`; рисунок в мире собран геометрическими ячейками.

Нижняя метка также имеет чёрный квадрат 0.40 м и белую подложку 0.50 м.
Её поверхность относительно `base_link`: (0,0,0.0146) м, нормаль −Z.
Она установлена под днищем, между колёсами. Оригинал ID 1:
[AprilRobotics](https://github.com/AprilRobotics/apriltag-imgs/blob/master/tag36h11/tag36_11_00001.png).

Список `tags` в обоих `config/cameras*.json` содержит размеры, положение и
`R_base_tag` для каждого ID; прежнее поле `tag` оставлено для совместимости
и описывает только верхнюю метку. Оси маркера: X вправо по рисунку, Y вверх,
Z наружу. Нижняя рамка повёрнута на 180° вокруг X корпуса.
Локализатор должен использовать преобразование соответствующего ID, а не
просто менять знак курса при обнаружении нижней метки. Детектор здесь ещё
не является готовой системой одометрии.

Тракт локализации поддерживает две выбираемые семьи маркеров:
`tag36h11` и `aruco4x4_50` (`DICT_4X4_50`, также принимается алиас
`4x4_dict_50`). Активная семья, допустимые ID и физический размер берутся из
`tags` файла калибровки; смешивать две семьи в одном track нельзя. Профиль
`coverage` использует полный масштаб, допускает маленькие маркеры, включает
инвертированные маркеры и применяет CLAHE/Otsu только когда исходный кадр дал
правдоподобный, но нераспознанный кандидат. Низкокачественные позы получают
увеличенную ковариацию, чтобы лидар имел больший вес при последующем fusion.

Создание изображения метки:

```bash
python3 scripts/generate_tag_texture.py --family aruco4x4_50 --id 0 --output /tmp/aruco_0.png
```

Размер в конфигурации — размер внешней чёрной границы, а не белой подложки.

Проверка перевёрнутого положения (после генерации перезапустите мир):

```bash
python3 scripts/generate_world.py --tag-rover-inverted
./scripts/run.sh
```

Обычное положение восстанавливается генерацией без `--tag-rover-inverted`.
При генерации повторно указывайте нужные style/seed и прочие параметры.
ID 1 проверен на изображении потолочной камеры при перевёрнутом ровере.
Во время самого переворота обе метки могут быть видны ребром или закрыты:
непрерывная детекция на всех промежуточных углах не гарантируется.

Фильтр считает **обе метки одним и тем же ровером**: набор «своих» ID берётся
из списка `tags` калибровки. Без этого замок личности принимал `id 1` за чужой
объект и отбрасывал каждое измерение от единственной видимой метки — трек
уходил в `LOST` и не возвращался, потому что личность сбрасывается только при
перемотке часов или смене калибровки. Метка, которой нет в калибровке, трек
по-прежнему забрать не может.

Планировщик ROI целится **в обе плоскости метки** сразу (0.3654 м сверху и
0.2104 м снизу), а не только в верхнюю. На штатном пороге `--roi-min-px 160`
запаса хватало и без этого, но он держался на padding'е: при пороге 96 px и
уверенном треке 116 из 754 проверенных видов обрезали метку. Для камеры,
смотрящей строго вниз, обе проекции совпадают и окно не меняется.


```bash
gz topic -t /model/tag_rover/cmd_vel -m gz.msgs.Twist -p 'linear: {x: 0.3}, angular: {z: 0.15}'
gz topic -t /model/yolo_rover/cmd_vel -m gz.msgs.Twist -p 'linear: {x: 0.3}, angular: {z: -0.15}'
# Остановка — команды действуют до следующей команды, тайм-аута нет
gz topic -t /model/tag_rover/cmd_vel -m gz.msgs.Twist -p 'linear: {x: 0}, angular: {z: 0}'
gz topic -t /model/yolo_rover/cmd_vel -m gz.msgs.Twist -p 'linear: {x: 0}, angular: {z: 0}'
```

Случайный заезд обоих роверов для набора покрытия (только для оценки,
рантайм этот скрипт не импортирует):

```bash
python3 scripts/drive_random.py --seconds 60 --speed 5 --seed 4242
```

Seed печатается и принимается, поэтому показательный заезд воспроизводим.
В отличие от фиксированного маршрута в `record_gazebo_truth.py`, случайные
точки проходят по всей арене и сводят роверы близко друг к другу.

`/model/tag_rover/pose` и `/model/yolo_rover/pose` — истинные позы в мире,
`gz.msgs.Pose_V`, 30 Гц. `/model/<имя>/odometry` — колёсная одометрия,
не эталон положения в мире. Центр bounding box не обязательно соответствует
центру ровера; учитывайте выбранную высоту и опорную точку при проекции.

### Что измерено по двум роверам

Заезд по случайным точкам до 5 м/с, истина из Gazebo (рантайм её не видит):

| | ровер с меткой | ровер без метки |
|---|---|---|
| доля валидных публикаций | 100% | 6.3% |
| ошибка XY | 0.6 см медиана, 2.7 см p95 | 10 см медиана, 33 см p95 |
| возраст измерения | 43 мс медиана, 67 мс p95 | 243 мс медиана |

**Второй ровер практически не отслеживается, и дело не в детекторе.** Веса
YOLO обучены (`artifacts/post-reboot/training/rover/weights/best.pt`, класс 1
= `opponent`) и на живых кадрах симулятора находят оппонента с уверенностью
0.79–0.87. На held-out тестовом сплите связка YOLO + `localize_box` даёт
1.9 см медианы и 5.4 см p95. Теряется он на гейтах рантайма: боксы, касающиеся
края кадра, отбрасываются целиком, а из оставшихся видов часть не проходит
`box_fit_rms_px <= 8`. Сквозь гейты проходит около одного измерения в 250 мс
при `coast_ms` = 300, поэтому трек почти всё время в `REACQUIRING` и
публикуется невалидным.

Гейты тракта оппонента спроектированы под метку и к безметочному ровер не
применимы как есть. Для реальной системы обучение под конкретные роверы
недоступно, поэтому прорабатывается безметочный путь — см. ниже.

### Безметочная детекция: проверка на реальном материале

```bash
python3 tools/markerless_probe.py /путь/к/видео.mp4 --roi bottom
```

Инструмент для глаза, не рантайм: слева обводка, справа бинарная маска,
пороги на ползунках. Ничего не обучается на ровере, поэтому его внешность
роли не играет. Клавиши: `a` — обвести границу арены мышью (сохраняется
рядом с видео), `m` — переключить модель фона, `r` — перезаснять эталон,
`Пробел` — пауза, `s` — сохранить кадр, `q` — выход.

На видео с полигона движущийся ровер обводится в каждом кадре плотной
односвязной маской. Два вывода, которые стоит знать заранее:

- **граница арены сильнее любого порога** — все ложные сработки были за
  барьером (люди, мерцающие LED-панели), и контур убирает их разом;
- **неподвижный ровер адаптивной моделью не виден**: она его впитывает.
  Статический эталон (`m`) его видит, но ничего не забывает и реагирует на
  смену освещения. Ни одна из двух моделей сама по себе не достаточна.

Габариты противника снимаются один раз перед заездом: цель выделяется вручную
на кадре каждой камеры, её размер связывается с кластером 3D-лидара, и дальше
считается постоянным.

> **Задача со звёздочкой.** Габариты по ходу заезда не обновляются. Если от
> ровера отваливаются детали и он уменьшается, гейты по размеру кластера и
> предположение о высоте разъедутся с реальностью. Обновление габаритов на
> лету пока сознательно не делается.

## Проверка

```bash
gz sdf -k worlds/mocap_arena.sdf
.venv/bin/python -m pytest tests -q
# При запущенной симуляции:
.venv/bin/python scripts/check_sim.py
.venv/bin/python scripts/check_sim.py --move
```

Тесты нужно запускать из `.venv`, а не системным `python3`: в системном
OpenCV нет `cv2.aruco.generateImageMarker`, и 43 теста падают на импорте
маркеров, хотя код исправен.

Проверяются все шесть RGB-потоков и истинные позы; PPM-кадры сохраняются в
`/tmp/mocap-camera-check`. `--move` кратковременно двигает оба ровера,
используйте на свободном старте. Тесты проверяют пять стилей, воспроизводимость,
пределы ошибок, соответствие матриц поворотам Gazebo и пересечение луча с полом.
Разрешение и частота камер задаются в генераторе; производительность зависит от GPU.

## Графическое окружение этой машины

`run.sh` очищает пути GTK/GIO от VS Code Snap, вызывавшие конфликт `libpthread`.
При несовпадении загруженного драйвера NVIDIA с системными библиотеками он
подключает совпадающие локальные библиотеки из
`~/.cache/mocap-rover/nvidia-<версия>`, если они подготовлены. Сейчас там находится
595.91.07 из кэша deb-пакетов Ubuntu. Системные пакеты скрипт не изменяет.
Когда системный `nvidia-smi` работает, обход не включается.

Запуск без GUI с рендерингом камер: `./scripts/run.sh -s --headless-rendering`.
Начальный обзор GUI задан в `config/gui.config`.

Обновлённая сцена проверена 20.09.2026: GUI работает, все шесть изображений
получены, оба ровера двигаются. На кадре первой камеры AprilTag ID 0 распознан
при цветном свете и погрешностях установки через OpenCV с
`cornerRefinementMethod=cv2.aruco.CORNER_REFINE_APRILTAG`.
Для дефолтного seed=42 непокрытых точек на проверочной сетке не обнаружено.

Текущее состояние набора тестов: 261 проходит, 2 пропущено, падает
`test_scenarios.Scenarios::test_styles_preserve_installation`.

Если окно серое и Entity Tree пустое, хотя камеры публикуют изображения,
это сбой подключения/инициализации GUI, а не отсутствие моделей в SDF.
Завершите текущий запуск полностью и повторите `./scripts/run.sh`.
Скрипт блокирует одновременный запуск второго экземпляра через `flock`;
при сообщении о занятой арене дождитесь завершения предыдущего процесса.
