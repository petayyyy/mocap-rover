# Промпт 04 — единый тракт и минимальная задержка

Прочитай `docs/dataset_tz/README.md` и принятые отчёты 01–03. Цель: один код
для обоих роверов, бюджет вычислений не растёт с числом роверов линейно, и
возраст измерения на выходе минимален.

## Что сделать

1. **Один проход на кадр.** Для каждого кадра камеры: один вызов модели фона
   (если она нужна) и один список окон для всех треков. Окна обрабатываются
   батчем; маркер декодируется только в окнах, где ожидается tag_rover.
   Полнокадровый поиск — только по расписанию watchdog.
2. **Бюджет.** На ноутбуке с 6 потоками: P95 обработки кадра ≤ 5 мс,
   суммарная нагрузка CPU ≤ 60 % при реплее 1.0× сим-времени. Профиль по
   стадиям (декодирование, фон, окна, детектор, PnP, фильтр) в `timing.json`.
3. **Задержка.** Публикация фильтра 200 Гц, `measurement_age_ms` P95 ≤ 25 мс
   при `--transport-ms 15`. Отдельно показать, как возраст меняется при
   `--transport-ms 5/15/30`.
4. **Готовность к железу.** Все временные величины в рантайме из меток
   экспозиции; хук поправки по строке (`line_time_ns`) работает и покрыт
   тестом с синтетическим сдвигом; клиент CM4 (будущий) не требуется, но
   интерфейс приёма кадров должен принимать `stamp_ns` и `row0`/`line_time_ns`
   от источника.
5. **Отказоустойчивость.** Реплей с `--cameras camera_1,camera_3,camera_5`
   (половина камер) и с `--no-lidar`: критерии P95 могут ослабнуть до 0.25 м,
   но подмен идентичности 0 и valid ≥ 90 %.
6. **Документ.** `docs/shared_rover_tracking.md`: схема тракта, где
   различаются tag_rover и opponent, все параметры с обоснованием числами из
   датасетов.
