# Промпт 07 — контур «камера → сеть → тракт» в Gazebo: окна, кодек, канал, задержка, покрытие

Прочитай `docs/dataset_tz/README.md`, `docs/handoff_window_size_answer.md`
(решение по окнам и форматам), `docs/cm4_camera_node_report.md` (измеренные
времена узла CM4/CM5 и объёмы), `docs/shared_rover_tracking.md`,
`localization_contracts/frame_source.py`, `lan_capture.py`,
`pi_cam/lan_protocol.py`, `scripts/replay_dataset.py`. Тракт локализации
не менять, кроме потолков окон и выбора формата в планировщике.

## Цель

Показать на датасете раскладки пяти креплений (`mocap_arena_mounts5`, промпт 06) и на датасете 03, что принятая конфигурация железа —
маркер в окне до 320×320 без потерь, соперник до 480×480 в JPEG q90
(до 640 при нехватке), полный кадр только по расписанию, шесть камер в
один гигабитный порт вместе с лидаром, узел CM4 — даёт ту же точность и
покрытие, что идеальная доставка, и укладывается в канал. Всё
эмулируется в реплее; железо не нужно.

## Что сделать

1. **Потолки окон.** `--roi-max-px 320`, `--opponent-roi-max-px 480`,
   расширение до 640 только сменой формата на JPEG. Планировщик при
   запросе окна больше потолка без потерь переводит это окно в JPEG, при
   запросе больше 640 — полный кадр по расписанию watchdog, не чаще
   раза в 0.25 с на камеру (как сейчас после `roi_exhausted`).
2. **Эмуляция кодека.** Флаг `--link-emulation cm4|cm5|ideal`. В режимах
   `cm4`/`cm5` каждое окно, помеченное JPEG, кодируется и декодируется
   (`cv2.imencode` q90, серое) перед подачей в тракт; окна без потерь
   не трогаются. Для `cm4` дополнительно эмулируется байеровская
   мозаика: серый кадр Gazebo превращается в псевдо-Bayer 2×2
   (каналы ±5 % усиления, как измерено на CM4 «0.8 % в темноте,
   больше при ярком свете» — взять 5 % как пессимизм), и приёмник
   восстанавливает серое демозаикой (`cv2.cvtColor ... BayerBG2GRAY`),
   а не картой усилений. Это проверяет путь `lan_capture.py`, который
   пойдёт на железе; реализовать демозаику там, тестом покрыть.
3. **Модель задержки.** `--transport-ms` заменяется расчётом по окну:
   `t = floor + t_node(size, format) + t_wire(bytes) + t_queue`, где
   `floor` = 22.6 мс (cm4) или 15.3 мс (cm5), `t_node` — из таблицы
   отчёта узла (вырезка + JPEG по размеру окна), `t_wire` = байты / 940
   Мбит/с, `t_queue` — очередь общего порта: все окна всех камер одного
   момента времени сериализуются на одном порту в порядке прихода,
   лидар занимает 22.5 Мбит/с постоянно. Момент прихода в тракт —
   экспозиция первой строки + `t`. Измерение маркера, как сейчас, по
   строке (`--line-time-ns 9452` в этом режиме включён, но только для
   времени, не для геометрии: датасет Gazebo с глобальным затвором,
   поэтому геометрическая поправка по строке в режиме эмуляции
   отключается флагом, и это надо явно объяснить в отчёте).
4. **Учёт канала.** В `timing.json` — ряд по времени: Мбит/с на порту с
   шагом 100 мс, P50/P95/max, доля времени выше 900 Мбит/с, число
   окон, переведённых в JPEG из-за потолка, число полных кадров.
   Режим захвата без трека: полные кадры не 83 к/с, а не чаще 10 к/с на
   камеру (`--acquire-full-frame-hz 10`), пока трека нет.
5. **Покрытие.** Новая метрика в отчёте реплея и в `status.json`: доля
   сим-времени, когда маркер tag_rover *мог* быть виден (эталон в поле
   зрения хотя бы одной камеры при падении ≤ 65° и стороне ≥ 20 px) и
   доля, когда он *был* принят хотя бы одной камерой; то же для
   силуэта соперника (верх корпуса в поле зрения при ≤ 65°). Разница —
   это потери тракта, а не раскладки камер. Считается по эталону,
   поэтому только в оценочном инструменте: новый `scripts/coverage_report.py`
   (evaluator-side, читает `truth.jsonl`), с тестом; в рантайм не попадает.
6. **Эксперимент.** Матрица прогонов на датасете mounts5 и на 03, транспорт по модели п. 3:
   - `ideal` (как сейчас, транспорт 25 мс, без кодека) — база;
   - `cm5`, `cm4` с окнами 320/480;
   - `cm4` с окнами 240/480 и 320/640 — чувствительность к потолкам;
   - `cm4`, силуэт без потерь, но не больше трёх камер на соперника
     (запасной вариант из ответа дирижёра);
   - `cm4` при `--gain 0.6` — JPEG на тёмной сцене.
   Для каждого: точность обоих роверов, valid, подмены, возраст P50/P95,
   покрытие, канал P95/max, доля JPEG-окон, время кадра ноутбука с учётом
   декодирования JPEG (измерить, оно входит в `latency_ms`).

## Критерии приёмки

| Метрика | Порог |
|---|---|
| Точность и valid в `cm4` 320/480 против `ideal` | ухудшение ≤ 10 % по P95, valid ≥ 99.9 %, подмен 0 на обоих датасетах |
| Канал в `cm4` 320/480 | P95 ≤ 750 Мбит/с, max ≤ 940, время выше 900 Мбит/с = 0 |
| Возраст измерения `cm4` | P95 ≤ 40 мс; `cm5` P95 ≤ 32 мс (синхронные камеры Gazebo, см. журнал) |
| Покрытие маркера, доля «мог быть виден» | ≥ 98 %; «принят» не ниже «мог» минус 1 % |
| Покрытие силуэта | «принят» не ниже «мог» минус 2 % |
| `--gain 0.6` в `cm4` | те же пороги точности |
| Тесты | зелёные; демозаика, кодек, модель задержки, покрытие — с тестами |

проходит, назвать причину с числами.
