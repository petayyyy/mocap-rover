# План закрытия трёх оставшихся проверок

Три задачи из отчёта `gazebo_run_20260926_results.md`, которые остались
непроверенными. Для каждой: что мешает сейчас (измерено, не предположено),
что менять, как проверять, критерий приёмки и чего проверка не покажет.

Порядок по ценности: **C (два ровера) → B (скорость) → A (геометрия камер)**.

## A. Геометрия центральных камер: 28° / yaw 90–270

### Что мешает сейчас

Ничего. `export_camera_config` выводит `K` и `R_world_optical` прямо из мира,
поэтому вариантный мир не требует ручной перекалибровки — она пересчитается
сама. Поза камеры в SDF кодируется как `x y z 0 (π/2 − tilt) yaw`, то есть
изменение наклона и азимута — правка одного числа на камеру.

### Что менять

| Файл | Правка |
|---|---|
| `scripts/set_camera_geometry.py` (новый) | переписать позу центральной пары из `(tilt, yaw, separation)`; по образцу `set_world_camera_model.py` |
| — | остальное не трогается: мир → калибровка → прогон уже автоматизированы |

### Как проверять

```bash
for v in "40 35 0.60" "28 90 0.60" "28 0 0.60" "30 90 0.60"; do
  set -- $v
  python3 scripts/set_camera_geometry.py worlds/mocap_arena_l2.sdf \
      --tilt $1 --yaw $2 --separation $3 --output /tmp/arena_$1_$2.sdf
  python3 scripts/run_tag_coverage_experiment.py --world /tmp/arena_$1_$2.sdf \
      --output artifacts/geom_$1_$2 --speed 0.5 --lane-spacing 0.5 --headless
done
```

### Чем мерить — и почему не тем, чем кажется

**Слитая ошибка для этого сравнения бесполезна.** Она уже 18.5 мм при допуске
200 мм; разница между вариантами утонет в шуме прогона. Геометрия покупает не
точность, а **запас**, и мерить надо его:

| Метрика | Откуда |
|---|---|
| `P(≥1 камера решает PnP)` по моментам времени | `camera_frames.csv`, поле `pnp_valid` |
| **`P(≥2 камеры решают PnP)`** — основная | то же |
| карта `pnp_rate` по клеткам 1 м | `spatial_bins.csv` |
| медиана incidence принятых наблюдений | `observations.csv`, поле `incidence_deg` |

Нужно добавить `n_cameras_solving` в `summary.json` — сейчас считается
вручную из CSV.

### Критерий приёмки

Вариант выигрывает, если `P(≥2)` растёт **≥ 5 пп** без потери `P(≥1)`.
Прогноз модели: 52.3 % против 48.3 % — это **+4 пп, то есть на границе
разрешающей способности одного прогона**. Скорее всего понадобятся два
прогона на вариант, чтобы отличить от шума.

### Чего не покажет

- Ничего про железо: на реальных камерах смена наклона требует полной
  перекалибровки внешних параметров всех шести.
- Ничего про motion blur: Gazebo его не рендерит.
- Ничего про западную полосу `x < 1 м` — измерено, что её не закрывает ни
  одна ориентация центральной пары.

**Оценка: 4 варианта × 12 мин = 1 час. Ценность сейчас низкая.**

## B. Развёртка по скорости до 11.11 м/с

### Что мешает сейчас — четыре факта из мира, все измерены

**1. Ровер физически не может ехать быстрее 1 м/с.**

```xml
<max_linear_velocity>1</max_linear_velocity>
<max_angular_velocity>2</max_angular_velocity>
```

11.11 м/с сейчас не «непроверено», а **недостижимо**. Это правка мира, а не
локализации.

**2. Камеры 15 Гц.** При 11.11 м/с это 0.74 м между кадрами. Нужно 90 Гц,
то есть 6 × 90 = 540 кадров/с рендера.

**3. Truth 30 Гц** (`PosePublisher update_frequency`). При 11.11 м/с это
0.37 м между отсчётами истины, а анализатор интерполирует линейно. Ошибка
измерения ошибки станет больше самой ошибки. Нужно ≥ 200 Гц.

**4. Арена не позволяет держать 11.11 м/с по кругу.** При `ω ≤ 1.5 рад/с`
(ограничение контроллера) и вписанном радиусе 5.2 м максимум `v = ω·r =
7.8 м/с`, и это уже 11.7 м/с² ≈ 1.19 g боковой перегрузки. Значит
змейка-lawnmower для этого режима не годится: нужны **разгонные проходы по
диагонали**. При `a = 8 м/с²` разгон до 11.11 м/с занимает 7.7 м, на
диагонали 14.7 м остаётся ≈ 0.6 с на полной скорости за проход.

### Что менять

| Файл | Правка |
|---|---|
| `scripts/set_world_rates.py` (новый) | `update_rate` камер, `update_frequency` PosePublisher, лимиты DiffDrive — одним скриптом, чтобы вариант мира был воспроизводим |
| `scripts/run_tag_coverage_experiment.py` | `--pattern {lawnmower,dash}`; dash — проходы по диагонали с разгоном и торможением |
| `scripts/analyze_tag_coverage.py` | разбивка метрик по скорости (поле уже есть: `truth_vx/vy`) |

### Методологическая ловушка, которую надо закрыть заранее

При 540 кадрах/с рендера RTF упадёт заметно ниже 1. Тогда Python-рантайм
получает **больше настенного времени на секунду симуляции**, и задержка,
измеренная в симвремени, окажется лучше, чем на железе. Сейчас RTF ≈ 1.0 и
числа честные; при 90 Гц это перестанет быть так.

Поэтому в прогон обязательно писать `real_time_factor` и докладывать
задержку **двумя числами**: в симвремени и в пересчёте
`latency_sim / RTF`. Без этого цифра ничего не значит.

### Как проверять

```bash
python3 scripts/set_world_rates.py worlds/mocap_arena_l2.sdf \
    --camera-hz 90 --truth-hz 200 --max-linear 12 --output /tmp/arena_fast.sdf
for v in 1 2 4 6 8 11.11; do
  python3 scripts/run_tag_coverage_experiment.py --world /tmp/arena_fast.sdf \
      --pattern dash --speed $v --output artifacts/speed_$v --headless
done
```

### Критерий приёмки

| Метрика | Порог |
|---|---|
| P95 measurement age | ≤ 40 мс при камерах 90 Гц |
| потерянных кадров | 0 |
| XY P95 | растёт не быстрее `v × age` — то есть ошибка объясняется экстраполяцией, а не развалом трека |
| ID switches | 0 на всех скоростях |
| `out_of_sequence` | > 0 и `dropped_too_old` = 0 — репропагация работает, история не переполняется |

Последняя строка важна: при 90 Гц и шести камерах out-of-sequence станет
массовым, и это первый режим, где история состояний может не хватить.

### Чего не покажет

- **Motion blur.** Gazebo рендерит идеально резкий кадр. При 11.11 м/с и
  экспозиции 1 мс реальный смаз — 11 мм в мире, на 3 м и `f≈245` это 0.9 px,
  при 5 мс — 4.5 px, что убивает субпиксельное уточнение углов. Recall на
  скорости в симуляции будет **оптимистичным**.
- Rolling shutter и реальную экспозицию.
- Deskew лидара: `gz gpu_lidar` рендерит всю сетку мгновенно, `--lidar-sweep-s 0`
  здесь корректен и неверен для железа.

**Оценка: подготовка мира и паттерна ≈ полдня, 6 прогонов × 15–40 мин
(RTF < 1) ≈ 2–4 часа. Ценность высокая.**

## C. Пересечение двух роверов

### Что мешает сейчас

`yolo_rover` **не несёт метки**: 15 визуалов, 0 ячеек тега (у `tag_rover` —
93). И эксперимент его удаляет (`opponent_removed: true`). То есть защита
личности сейчас проверена только юнит-тестами на синтетических сканах.

### Что менять

| Файл | Правка |
|---|---|
| `scripts/add_marker_to_model.py` (новый) | нанести маркер заданного ID на модель: 8×8 ячеек 0.05 м, та же схема имён и координат, что у `tag_rover` (`tag_<id>_<r>_<c>`, от −0.175 до +0.175) |
| `scripts/run_tag_coverage_experiment.py` | `--keep-opponent`; второй командир, ведущий `yolo_rover` по встречному маршруту; truth для обоих роверов |
| `scripts/analyze_tag_coverage.py` | расстояние оценки до **каждого** ровера |

### Решающая метрика, которой сейчас нет

**Доля опубликованных сэмплов, где оценка ближе к сопернику, чем к своему
роверу.** Это и есть ID switch. Сейчас не измеряется нигде: `id_rejections`
считает отклонённые наблюдения, а не подмену.

Дополнительно: `ambiguous_cluster`, `merged_cluster`, переходы в
`REACQUIRING` во время сближения.

### Сценарии

| # | Сценарий | Что проверяет |
|---|---|---|
| 1 | Встречное пересечение, боковой зазор 2.0 / 1.0 / 0.5 / 0.3 м | лидарные гейты на реальных сканах |
| 2 | **Пересечение внутри полосы `x < 1 м`** | состязательный случай бесплатно: там камеры уже теряют метку, то есть «маркер скрыт + соперник рядом» без искусственного отключения |
| 3 | Соперник вообще без метки | худший случай: нечем подтвердить, кто есть кто |
| 4 | Соперник с меткой другого ID, проезжающий вплотную | `_identity_matches` на живых данных |

Сценарий 2 — самый ценный и ничего не стоит: западная полоса уже
воспроизводимо гасит камеры каждый заезд.

### Критерий приёмки

- **0 сэмплов, где оценка ближе к сопернику.** Не «мало» — ноль.
- При зазоре < 0.5 м трек обязан уйти в `REACQUIRING`, а не следовать за
  кем-то. Потеря валидности здесь — правильный ответ, а не провал.
- Каждый `ambiguous_cluster` / `merged_cluster` объясним по геометрии.
- После расхождения трек восстанавливается **только по метке**.

### Чего не покажет

- Оба ровера здесь несут разные метки; одинаковые корпуса без меток —
  отдельный вариант (сценарий 3), и он строже.
- Тени и люди как foreground: MOG2 в рантайм не подключён.

**Оценка: генератор метки + второй командир ≈ полдня, 4 сценария × 12 мин
≈ 1 час. Ценность наивысшая — это единственное непроверенное требование
безопасности.**
