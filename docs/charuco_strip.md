# ChArUco-полотно 12×3 м для внешней калибровки арены

Одно длинное ChArUco-полотно на полу, которое видят сразу все потолочные
камеры. Его шахматные углы — общие точки, по которым решаются взаимные
положения камер, начало координат арены и связь 3D-лидара с камерами.
Внутренние параметры (K, D) калибруются отдельно ручной доской; здесь только
напольная мишень.

Инструмент: `tools/charuco_strip.py`. Готовые файлы: `assets/charuco_strip/`,
модель для Gazebo: `models/charuco_strip/`.

## Выбранная раскладка

| | |
|---|---|
| полотно | **12.000 × 3.000 м** |
| белая кайма | **375 мм** с каждой из четырёх сторон (одна клетка) |
| доска внутри каймы | 30 × 6 клеток = 11.250 × 2.250 м |
| клетка шахматки | **375 мм** |
| маркер | **280 мм** (0.75 клетки), белое поле вокруг маркера 47.5 мм |
| ячейка кода | 40 мм (5×5 бит + рамка = 7 ячеек) |
| словарь | **DICT_5X5_250**, ID 0…89 |
| шахматных углов | 29 × 5 = 145 |
| OpenCV | `cv2.aruco.CharucoBoard((30, 6), 0.375, 0.280, DICT_5X5_250)`, не-legacy раскладка |

Раскладка совпадает с `CharucoBoard.generateImage(..., marginSize=кайма)`
пиксель в пиксель (`python3 tools/charuco_strip.py selftest`,
`tests/test_charuco_strip.py`). Первая клетка доски (за каймой, левый верхний
угол) чёрная; маркер ID 0 — во второй клетке первой строки; ID растут по
строкам. Система координат доски по OpenCV: начало в левом верхнем углу
**доски** (не полотна), x вправо вдоль длинной стороны, y **вниз** по листу,
z из листа. Координата на полотне = координата доски + 375 мм по обеим осям.

## Почему такие размеры

Реальная оптика — Waveshare IMX219-160: 160° по диагонали на полном сенсоре
3280×2464. В приближении равноугольного (equidistant) объектива это даёт
f ≈ 573 px/рад для кадра 1280×960 (≈128° по горизонтали, ≈96° по вертикали).
Существующий `models/imx219_1280x960.yaml` снят с кропом сенсора и для
расчёта не использовался.

Для камеры на высоте h = 2.9 м точка пола под углом θ от надира занимает
`f·cos²θ / h` пикселей на метр в радиальном направлении:

| θ от надира | расстояние по полу | px/м (1280×960) | клетка 375 мм | ячейка 40 мм |
|---:|---:|---:|---:|---:|
| 0° | 0 м | 198 | 74 px | 7.9 px |
| 30° | 1.7 м | 148 | 56 px | 5.9 px |
| 45° | 2.9 м | 99 | 37 px | 4.0 px |
| 60° | 5.0 м | 49 | 19 px | 2.0 px |

Порог уверенного чтения ArUco в реальных условиях — около 4 px на ячейку
кода, шахматный угол уточняется субпиксельно уже при клетке 15–20 px. Значит
маркеры 280 мм читаются в радиусе ≈3 м от проекции камеры, а углы шахматки —
до ≈5 м. Этого хватает, чтобы каждая камера в каждом положении полотна видела
≥65 углов (см. ниже), а соседние камеры видели одни и те же клетки.

### Синтетическая проверка по сцене Gazebo

`evaluate` берёт позы камер прямо из SDF-мира (модель → звено → сенсор,
оптическая ось Gazebo +X), рисует полотно на полу через модель реального
объектива (а не через 105° pinhole, который стоит в мире), добавляет размытие
0.7 px и шум, и прогоняет `CharucoDetector`. Мир `mocap_arena_l2.sdf`
(4 угловые камеры вниз + 2 центральные под 40°), полотно вдоль X, три
положения центральной линии (Y = 4, 6, 8 м), кадр 1280×960, итоговое полотно
30×6 клеток по 375 мм с каймой:

| положение | углов на камеру (из 145) | ячейка, px (медиана) | ложных ID |
|---|---|---:|---:|
| Y = 4 | 65…107, каждая из 6 камер ≥65 | 3.1…6.1 | 0 |
| Y = 6 | 79…80, все 6 камер | 4.4…4.9 | 0 |
| Y = 8 | 65…105, каждая из 6 камер ≥65 | 3.1…6.1 | 0 |

Сравнение кандидатов на той же сцене (полные результаты первого перебора
делались для доски без каймы 32×8; относительные выводы те же):

| вариант | клетка/маркер, мм | словарь | ячейка, px (медиана) | ложных ID | комментарий |
|---|---|---|---:|---:|---|
| **выбран** | 375 / 280 | 5X5_250 | 4.4 | 0 | ≥4 px до θ ≈ 45° |
| плотнее (38×8 с каймой) | 300 / 225 | 5X5_250 | 3.5 | 0 | углов больше (68…167), но ячейка без запаса |
| крупнее | 500 / 375 | 5X5_250 | 5.9 | 0 | запас для 640×480, углов вдвое меньше |
| ещё плотнее | 250 / 187.5 | 5X5_1000 | 3.0 | 2–4 | словарь на 1000 начинает путать |
| меньше бит | 375 / 280 | 4X4_250 | 5.1 | **9–29** | расстояние Хэмминга 1 — ложные ID |
| больше бит | 375 / 280 | 6X6_250 | 3.9 | 0 | чуть меньше находок, выигрыша нет |

- **4X4 отпадает**: при ~100 маркерах в кадре словарь с расстоянием Хэмминга 1
  даёт ложные ID даже на синтетике. 5X5_1000 тоже начинает путать.
- **300 мм** даёт больше углов, но ячейка 3.5 px — без запаса на реальную
  оптику, JPEG и виньетирование. 375 мм держит ≥4 px при θ ≤ 45°.
- **500 мм** (22×4 клетки с каймой 500 мм) — запасной вариант, если
  калибровочные кадры придётся снимать в 640×480 с полным полем зрения: там у
  375 мм ячейка 2.2–3.1 px, у 500 мм 2.9–4.2 px.
- Pinhole-камера из мира (`--lens sim`) показывает ячейку 6.7 px и меньше
  углов у края — симулятор **переоценивает** разрешение на периферии и не
  показывает фишай-искажений. Судить о размере по картинке из Gazebo нельзя.
- Мир `mocap_arena.sdf` (сетка 2×3): положения Y = 4 и 8 дают по 105–111
  углов четырём камерам двух соседних рядов; Y = 6 видит целиком только
  средний ряд (101–106 углов), крайние ряды — по 15–22.

**Главная рекомендация по съёмке:** внешняя калибровка не обязана идти на
рабочей частоте кадров. Снимайте стоп-кадры в максимальном режиме сенсора
(1640×1232 или 3280×2464): положение камеры от режима не зависит, а
ячейка становится 10–20 px. Нужна лишь калибровка K, D именно того режима,
в котором снимаются кадры, плюс K, D рабочего режима для рантайма.

Редактор проверен: загруженный проект совпадает с растром по всем ячейкам
маркеров и клеткам. В редакторе можно добавить подписи и логотипы в каймe
и белых полях, но не двигать клетки: раскладка должна остаться раскладкой
OpenCV.

### Печать

- Баннерная ткань или ПВХ, **матовая**, ширина рулона ≥3.0 м (обычно 3.2 м):
  полотно печатается одним куском без стыков. Если печатают со стыком, стык
  должен идти по границе клеток и ни одна клетка не должна собираться из
  двух кусков.
- Кайма 375 мм уже в файле: люверсы и подгиб делать в ней, край доски не
  трогать. Крайние маркеры отстоят от края полотна на 422.5 мм.
- После печати измерьте рулеткой длину всех 30 клеток и всех 6 клеток.
  Фактический шаг (например 374.6 мм вместо 375) вносится в
  `CharucoBoard(...)` вместо номинала; иначе весь масштаб арены уедет
  на ту же долю процента.
- Полотно должно лежать плоско и не тянуться: при 0.5 % растяжения 12 м
  превращаются в 12.06 м.

## Раскладка на арене

Полотно кладут длинной стороной вдоль X, верхним краем печати (сторона
маркера ID 0) к +Y. Если `(x0, y0)` — положение левого верхнего угла
**полотна**, то `arena = (x0 + (x_board + 0.375), y0 − (y_board + 0.375), 0)`.
Формула записана и в `board.json`.

Рекомендуемые положения центральной линии для текущего мира с лидаром:

| положение | Y центра | кто видит | зачем |
|---|---:|---|---|
| 1 | 6.0 | все 6 камер, по 79–80 углов; лидар прямо над полотном | связывает всё сразу, задаёт центр арены и лидар |
| 2 | 4.0 | все 6 камер, 65–107 углов | второй ракурс для угловых камер (3,3) и (9,3) |
| 3 | 8.0 | все 6 камер, 65–105 углов | второй ракурс для (3,9) и (9,9) |

Положения полотна не обязаны быть известны заранее: поза полотна в каждом
положении — неизвестная в общей оптимизации, а камеры связываются через
общие углы. Центр и оси арены задаёт **одно** положение (например, 1),
выставленное по бортам рулеткой: край полотна параллельно борту, отступ
измерен. Точность выставления и есть точность привязки к арене.

## Лидар

RoboSense Airy в `(6, 6, 2.75)` смотрит вниз: шаг лучей 0.4° по азимуту и
0.947° по каналам. На полу это 1.9 × 4.5 см в надире, 2.7 × 9 см под 45°,
3.8 × 18 см под 60°. Клетка 375 мм под 45° накрывается 4 кольцами по 14 точек,
так что по **интенсивности** отражения шахматка читается примерно в радиусе
3.5 м от надира лидара (положение 1 полотна). Накопите 30–50 статичных
сканов, соберите карту интенсивности пола и подгоните к ней сетку клеток —
это даёт лидару X, Y и курс; плоскость пола даёт крен, тангаж и высоту.

Если интенсивности не хватает, поставьте на известные клетки полотна два-три
предмета с чёткой геометрией (коробки 30–40 см): лидар видит их как объёмы,
камеры — их положение на клетках.

## Gazebo

```bash
# Модель в мир (по умолчанию mocap_arena_l2.sdf, центральная линия Y = 6)
python3 tools/charuco_strip.py place --strip-y 6
python3 tools/charuco_strip.py place --world worlds/mocap_arena.sdf --strip-y 4
python3 tools/charuco_strip.py place --remove
./scripts/run.sh
```

`run.sh` уже добавляет `models/` в `GZ_SIM_RESOURCE_PATH`. Начало модели —
левый верхний угол полотна, поэтому `place` ставит позу `(0, Y+1.5, 0.001)`.
В GUI проверьте, что маркер ID 0 оказался у угла с меньшим X и большим Y;
если текстура зеркальна, это UV-соглашение загрузчика, а не раскладка.
Помните: камеры мира — pinhole 105°, кадры симулятора не воспроизводят
разрешение и искажения реальной оптики на периферии.

## Мир с реальной оптикой: `worlds/mocap_arena_charuco.sdf`

Отдельный мир для проверки детекции в симуляторе. Сделан из
`mocap_arena_l2.sdf` (те же позиции камер и лидар), но камеры заменены на
`wideanglecamera` Gazebo с равноугольной линзой: 160° по диагонали кадра
1640×1232 — это полнокадровый режим IMX219 (`1640x1232-RGB888`), из которого
libcamera отдаёт сенсор целиком. Полотно лежит по центру пола: левый верхний
угол в `(0, 7.5)`, центр в `(6, 6)`, прямо под лидаром.

| | |
|---|---|
| f | 734.5 px/рад (`r = f·θ`), главная точка (820, 616) |
| HFOV / VFOV | 2.2327 рад (127.9°) / 1.6773 рад (96.1°) |
| `cutoff_angle` | 1.4163 рад (81.2°, чуть дальше угла кадра) |
| `env_texture_size` | 2048 (грань кубической карты; меньше — теряется резкость у края) |

```bash
python3 tools/charuco_strip.py world          # пересобрать мир и config/mocap_arena_charuco_cameras.json
MOCAP_WORLD=worlds/mocap_arena_charuco.sdf ./scripts/run.sh
./scripts/check_charuco_poses.py
python3 scripts/check_sim.py                  # PPM-кадры всех камер в /tmp/mocap-camera-check
python3 tools/charuco_strip.py detect --board assets/charuco_strip/charuco_strip_12x3_board.json /tmp/mocap-camera-check/*.ppm --save-dir /tmp/detected --json-out /tmp/corners.jsonl
```

`check_charuco_poses.py` ждёт по одному кадру от каждой камеры, проверяет
детекцию ChArUco и решает fisheye PnP по найденным углам. Карта маркеров по
умолчанию берётся из
`tools/charuco_strip_editor/charuco_strip_12x3/charuco_strip_12x3_map.txt`.
Для каждой камеры печатаются координаты относительно центра полотна и центра
поля, ошибка репроекции и отклонение от позы в SDF. Подробный JSON и кадры с
нарисованными детекциями записываются в `/tmp/mocap-charuco-check/`. Там же
создаются `scene_3d.png` и масштабируемый `scene_3d.svg`: поле 12×12 м,
полотно ChArUco, положения камер, их пирамиды обзора и направления оптических
осей. Ракурс можно поменять параметрами `--view-elev` и `--view-azim`, а
размер поля — через `--field-size WIDTH HEIGHT`.

Интерактивное окно берёт по одному кадру с каждой камеры, один раз вычисляет
позы, закрывает видеопотоки и показывает готовую сцену. Схему можно свободно
вращать мышью и масштабировать колёсиком; повторной детекции и перерисовки нет:

```bash
# Из запущенного Gazebo
./scripts/check_charuco_poses.py --live-3d

# Непосредственно из MJPEG-потоков реальных Raspberry Pi, без Gazebo
./scripts/check_charuco_poses.py --live-3d \
  --camera-source camera_1=http://IP_CAMERA_1:8080/video_feed \
  --camera-source camera_2=http://IP_CAMERA_2:8080/video_feed \
  --camera-source camera_3=http://IP_CAMERA_3:8080/video_feed \
  --camera-source camera_4=http://IP_CAMERA_4:8080/video_feed \
  --camera-source camera_5=http://IP_CAMERA_5:8080/video_feed \
  --camera-source camera_6=http://IP_CAMERA_6:8080/video_feed
```

`--camera-source` также принимает номер устройства (`camera_1=0`), путь
`/dev/video*`, RTSP URL или любой поток, который открывает OpenCV. Получение
шести потоков выполняется параллельно. Параметры fisheye автоматически
масштабируются, если реальный MJPEG имеет уменьшенное разрешение, например
820×616 вместо 1640×1232.
Офлайн-проверка ранее сохранённых `camera_1.ppm` … `camera_6.ppm`:

```bash
./scripts/check_charuco_poses.py --images-dir /tmp/mocap-camera-check
```

Оси системы с центром ChArUco: `+X` вдоль длинной стороны, `+Y` к верхней
стороне с первыми ID, `+Z` вверх. В этом мире центр полотна и центр поля
совпадают: `(6, 6, 0)` в системе арены.

`config/mocap_arena_charuco_cameras.json` содержит модель линзы, позы камер
из SDF и положение полотна. Ожидаемый результат по синтетике (та же модель
линзы, размытие 0.7 px, шум) лежит в
`assets/charuco_strip/expected_detection_mocap_arena_charuco.csv`: каждая из
шести камер видит 51 из 90 маркеров и 80 из 145 углов, ложных ID нет,
ячейка кода 4.2–6.4 px, угол до 63° от надира. Истинные координаты всех
углов полотна в системе арены — в
`assets/charuco_strip/charuco_strip_arena_center_truth.csv`
(`kind,id,corner,x_board_mm,y_board_mm,x_arena_m,y_arena_m,z_arena_m`).

Сравнивать с симулятором нужно так: число найденных маркеров и углов на
камеру против CSV, а точность — через проекцию истинных углов из
`truth.csv` моделью линзы из JSON. Если в Gazebo найдено заметно меньше,
первым делом смотреть `env_texture_size` и то, что рендер-движок ogre2
действительно собрал `wideanglecamera` (в логе не должно быть предупреждения
о неподдерживаемом типе сенсора). Wide-angle камера не публикует
`camera_info`; K для неё в pinhole-виде не существует.

## Команды

```bash
python3 tools/charuco_strip.py selftest
python3 tools/charuco_strip.py generate
python3 tools/charuco_strip.py evaluate --strip-y 4 6 8 --save-dir /tmp/charuco_eval
python3 tools/charuco_strip.py evaluate --resolution 640 480 --squares-x 22 --squares-y 4 --square-mm 500 --marker-mm 375
python3 tools/charuco_strip.py evaluate --lens sim
python3 tools/charuco_strip.py detect --board assets/charuco_strip/charuco_strip_12x3_board.json photos/*.png --save-dir /tmp/detected --json-out /tmp/corners.jsonl
```

Кайма по умолчанию равна клетке; `--border-mm` меняет её у любой команды,
`--squares-x/--squares-y` задают доску внутри каймы.

`detect` печатает число маркеров и углов на каждом снимке и пишет углы с ID
построчно в JSON — вход для решения внешних параметров. Само решение
(PnP каждой камеры к полотну, сшивка через общие углы, привязка лидара) в этом
инструменте не реализовано.
