# Замер на стенде: малый поток 640×480 + окна маркера (целевой профиль)

Что проверяем. Целевая схема передачи из реплея (`artifacts/replay_10_*`):
каждая камера шлёт весь кадр, уменьшенный на узле до 640×480, 30 Гц
(для соперника), а три камеры, ближайшие к роверу, — окна маркера 320×320
в полном разрешении на 83 Гц. Полных кадров 1640×1232 нет. Малые кадры
разных камер разнесены по фазе на общей шкале PTP, чтобы не приходить в
коммутатор одновременно. В реплее при этом маркер P95 16–17 мм на CM4
(эталон 14–15), канал ~560 Мбит/с.

Вопросы к железу:

1. Сколько CPU CM4 и миллисекунд стоит уменьшение кадра (`node reduce`).
2. Не растёт ли задержка окон маркера, когда рядом идёт малый поток.
3. Держит ли коммутатор профиль на шести камерах без потерь.

## Подготовка

На каждой CM4 (код из этого коммита, ничего больше не меняется):

```bash
sudo apt install -y python3-opencv          # уменьшение кадра ~2 мс; без него numpy, медленнее
sudo rsync -a --delete ~/mocap-rover/pi_cam/ /opt/mocap-rover/pi_cam/
sudo systemctl restart camera_node
```

`node_config.json` не меняется (`"stream": "raw"` на CM4 обязателен).
Проверка: в статусе узла появилось поле `scale_backend` = `opencv`.

На ноутбуке — тот же коммит, PTP как в прошлых прогонах (`camera_1` MASTER).

## Прогоны

Все команды из корня репозитория на ноутбуке. Сохраняйте `--json` и
полный вывод, как раньше.

### S1. Одна CM4, без малого потока (база), 60 с

```bash
.venv/bin/python scripts/lan_camera_timing.py --nodes 192.168.10.101:5600 \
  --seconds 60 --window-size 320 --window-format y8 --full-period 0 --clock-mode ptp \
  --json S1_cam1_windows320.json
```

### S2. Одна CM4, окна + малый поток, 60 с

```bash
.venv/bin/python scripts/lan_camera_timing.py --nodes 192.168.10.101:5600 \
  --seconds 60 --window-size 320 --window-format y8 --full-period 0 --clock-mode ptp \
  --small 640x480@30 --json S2_cam1_windows320_small640.json
```

Сравнить с S1: `window latency` P95, `node exp->send` P95, `cpu`, а также
новые строки `small stream`, `small latency`, `node reduce`.

### S3. Шесть CM4, целевой профиль, 600 с

```bash
.venv/bin/python scripts/lan_camera_timing.py --nodes 192.168.10.101:5600 192.168.10.102:5600 \
  192.168.10.103:5600 192.168.10.104:5600 192.168.10.105:5600 192.168.10.106:5600 \
  --seconds 600 --window-size 320 --window-format y8 --full-period 0 --clock-mode ptp \
  --window-nodes 3 --small 640x480@30 --small-stagger --json S3_six_target_600s.json
```

Окна получают первые три узла списка, малый поток — все шесть, со сдвигом
фаз.

### S4. То же без сдвига фаз, 120 с (для сравнения)

S3 с `--seconds 120` и без `--small-stagger`, `--json S4_six_target_inphase_120s.json`.

### S5. Если S3 даёт потери: шесть узлов, только малый поток, 120 с

S3 с `--seconds 120 --no-windows` вместо `--window-nodes 3`,
`--json S5_six_small_only_120s.json`. Покажет, ломает ли коммутатор сам
малый поток или только вместе с окнами.

Перед S3 и после каждого прогона снять счётчики пауз ноутбука:

```bash
ethtool -S enp0s31f6 | grep -i -E "flow|pause|xon|xoff"
```

## Критерии

| что | где в выводе | порог |
|---|---|---|
| окна маркера не теряются | `node missed`, `node dropped` | 0 (единицы на старте допустимы) |
| задержка окон | `window latency` P95 | ≤ 35 мс, и в S2 не больше S1 + 2 мс |
| малый поток идёт | `small stream` …/s | 29.5–30.5 кадра/с, `node skipped` ≈ 0 |
| задержка малого кадра | `small latency` P95 | ≤ 50 мс |
| уменьшение на узле | `node reduce` P95 | ≤ 10 мс |
| CPU CM4 | `node … cpu` P95 | ≤ 70 % |
| температура | `node … temp` max, `throttled` | < 75 °C, none |

Если не проходит только задержка окон или CPU на CM4 — это аргумент за
CM5 (там уменьшение делает ISP). Если в S3 теряют окна, а в S4 хуже, чем в
S3, — подтверждается, что ломают одновременные всплески, а не средняя
полоса.
