Проверено на живом железе 29–30.09.2026. Модуль — **CM5 Lite**, а не CM4:
финальная плата будет CM4, поэтому код и замеры сделаны без опоры на

Стенд: CM5 Lite + IMX219-160, `pi@10.42.0.158` по USB-Ethernet
(RTL8152, 100 Мбит/с) прямо в ноутбук. Сырые замеры:

## Откуда берётся задержка и почему 20 мс не достигнуто

Измерено отдельно на плате (`probe_pipeline.py`): от `SensorTimestamp` до
возврата `capture_request()` проходит **P50 15.23 мс, P95 16.04 мс**. Это
время платформы, до того как мой код увидит кадр. Разбор всей цепочки от
начала экспозиции первой строки:

| Участок | Время | Кто отвечает |
|---|---|---|
| Экспозиция первой строки | 0.79 мс | сенсор |
| Считывание 1232 строк | 11.64 мс | сенсор, rolling shutter |
| ISP (PiSP) и передача буфера в Python | ≈ 3.6 мс | libcamera/picamera2 |
| **Итого до кадра в Python** | **≈ 16.0 мс** | платформа |
| Вырезание окон | 0.34 мс | узел |
| JPEG двух окон 480×480 (simplejpeg) | ≈ 1.5 мс | узел |
| Очередь отправки и сокет | ≈ 0.5 мс | узел |
| **Итого экспозиция → отправка** | **18.33 мс** | измерено |
| Сеть 100 Мбит/с | 3.83 мс | стенд, не финальный канал |
| **Итого экспозиция → приём** | **21.98 мс** | измерено |

Вывод: 80 % бюджета в 20 мс съедает физика сенсора плюс конвейер платформы,
а не передача. Мой код добавляет 2.3 мс. На гигабите сетевой участок
падает до ≈ 0.3 мс, и P95 выходит около 19.7 мс — то есть порог достижим
только вплотную. Чтобы иметь запас, надо сокращать не передачу, а конвейер
захвата: на CM4 сырой поток `SBGGR8` не сжат (на CM5 CFE отдаёт
`PISP_COMP1`), и захват мимо ISP может снять около 3 мс. Это стоит
проверить на финальном CM4; в текущем коде путь через `YUV420`, как задано.

Отдельно: доставка кадра целиком означает, что окно нельзя отправить раньше,
чем дочитан последний ряд кадра, даже если само окно лежит в первых строках.
Это ограничение libcamera, не узла.

## Что такое `SensorTimestamp` на этой платформе

Светодиода на GPIO нет, поэтому привязка определена другим способом, который
даёт однозначный ответ без внешнего оборудования: **развёрткой по
экспозиции** (`probe_reference.py`). Кадр выдаётся после окончания
считывания. Если `SensorTimestamp` стоит на начале экспозиции, то
«метка → выдача» растёт ровно на прирост экспозиции; если на начале
считывания, не зависит от экспозиции вовсе.

| Экспозиция (факт) | Метка → выдача, P50 |
|---|---|
| 0.49 мс | 14.18 мс |
| 0.99 мс | 14.18 мс |
| 1.99 мс | 14.17 мс |
| 4.00 мс | 14.18 мс |
| 8.00 мс | 15.67 мс |

На восьмикратном изменении экспозиции (0.5 → 4 мс) задержка постоянна с
точностью 0.01 мс, наклон 0.000. Значит **`SensorTimestamp` не включает
экспозицию: это начало считывания первой строки**, и вариант по умолчанию
`stamp_reference = readout_start_first_row` верен, а
`stamp_ns = SensorTimestamp − exposure` даёт начало экспозиции первой
строки. Проверено на живом кадре: равенство
`stamp_ns == sensor_stamp_ns + clock_offset_ns − exposure_ns` выполняется.

Альтернативу «метка в конце кадра» этот тест формально не исключает, но она
требует 14.2 мс чистого ISP на 2 Мп, что для PiSP невероятно, тогда как
«начало считывания» даёт 14.18 − 11.64 = 2.54 мс ISP — правдоподобно.
Точку 8 мс исключаю из фита: там libcamera удлиняет обработку на 1.5 мс.

**Светодиодный тест всё равно нужен**: он даст абсолютную привязку и
измерит `line_time_ns`, чего развёртка по экспозиции не даёт.

## `line_time_ns`

Измерения нет. Регистровая модель IMX219 для этого режима: 9452 нс на
строку. Косвенное подтверждение — самосогласованность с измеренным
периодом кадра: 12.041 мс / 9452 нс = **1273.9 строки** = 1232 активных
плюс 42 строки гашения, что для этого режима правдоподобно; 1232 × 9452 нс
= 11.64 мс считывания укладывается в период 12.041 мс с зазором 0.4 мс.
Погрешность модели этим не измерена, порог «≤ 5 % по светодиоду» остаётся
непроверенным.

## PTP

Здесь два существенных факта, которые меняют план синхронизации.

**1. У CM5 есть аппаратные метки, но драйвер требует настройки.**

```text
PTP Hardware Clock: 0
hardware-transmit, hardware-receive, hardware-raw-clock
Hardware Transmit Timestamp Modes: off, on, onestep-sync
```

Программные метки драйвер **не поддерживает вовсе**: `ptp4l -S` падает с
`interface 'eth0' does not support requested timestamping mode`. С
аппаратными и таймаутом по умолчанию `ptp4l` уходит в `FAULTY`:

```text
timed out while polling for tx timestamp
increasing tx_timestamp_timeout may correct this issue
port 1: MASTER to FAULTY on FAULT_DETECTED
```

Рабочая команда найдена: `ptp4l -i eth0 -m --tx_timestamp_timeout 50` —
порт поднимается, узел берёт роль grandmaster. Это надо записать в
инструкцию развёртывания.

**2. У ноутбука через USB-адаптер аппаратных меток нет** (`PTP Hardware
Clock: none`, только software). Значит делать ноутбук мастером — худший
вариант: он ограничит точность программными метками. Лучше держать мастером
один из узлов (у CM4 и CM5 PHC есть), тогда узлы синхронизируются
аппаратно между собой, а это именно то, что требует ТЗ (ошибка между
узлами ≤ 100 мкс); ноутбуку общая шкала нужна только для оценки задержки.
Для финальной установки нужна либо сетевая карта с PHC на ноутбуке, либо
свитч с поддержкой PTP.

Мой код опроса проверен на живом `ptp4l`: в статусе появилось
`{"offset_ns": 0, "state": "MASTER"}` и то же значение дошло до заголовка
каждого кадра. Ноль здесь корректен: узел сам был мастером.

## Дефекты, найденные на железе, и что исправлено

Все пять нашлись только на живой камере или живом PTP и закрыты тестами.

1. **`BufferError: cannot close exported pointers exist`** при остановке
   камеры. `numpy`-вид на DMA-буфер жил дольше, чем освобождение запроса, и
   аллокатор picamera2 отказывался закрываться. Исправлено: `Frame.release()`
   сначала снимает ссылку на массив, `PicameraSensor.stop()` делает
   `gc.collect()`. После правки узел закрывает камеру чисто и по SIGTERM.
2. **`wait_connected()` возвращался по первому кадру, а не по приветствию.**
   Узел, у которого окна остались от прежнего клиента, начинает отдавать
   кадры сразу, и `hello()` оказывался пустым — `record_lan_dataset.py`
   падал на живом узле с `TypeError`. Исправлено: идентичность считается
   подтверждённой только по `HELLO` (множество `announced`), кадры при этом
   не теряются.
3. **`pmc` недостижим для узла.** Лежит в `/usr/sbin`, которого нет в PATH
   службы, и не может привязать свой сокет от непривилегированного
   пользователя (`uds: bind failed: Permission denied`). Исправлено:
   абсолютный путь по умолчанию и флаг `ptp_pmc_sudo` с одной строкой
   NOPASSWD; без прав поле остаётся пустым, а метки кадров не страдают.
4. **Инструмент замеров завышал объём канала для JPEG**: считал
   декодированные пиксели вместо байт на проводе (306 Мбит/с вместо
   реальных 11.5). Исправлено: `LanFrame.payload_bytes` несёт размер
   полезной нагрузки, его и считают `lan_camera_timing.py` и
   `record_lan_dataset.py` (в `meta.json` теперь `mbit_s_wire`).
5. **Опрос PTP засорял журнал**: каждый вызов через sudo пишет три строки
   в `journal`. Период опроса по умолчанию поднят с 1 до 5 с.

## Яркость при короткой экспозиции — предупреждение по проекту

ТЗ фиксирует экспозицию 0.5–1 мс. В обычной комнате этого мало:

| Экспозиция / усиление | Средняя яркость кадра | 99-й перцентиль |
|---|---|---|
| 0.5 мс / 4 | 17.1 | 35 |
| 0.8 мс / 4 | 18.2 | 45 |
| 0.8 мс / 8 | 20.6 | 66 |
| 1.0 мс / 16 | 28.8 | 103 |
| 2.0 мс / 16 | 39.7 | 148 |

При штатных 0.8 мс и усилении 4 кадр почти чёрный (18 из 255). Арену
придётся освещать существенно ярче — примерно в шесть раз против этой
комнаты, — иначе ArUco не наберёт контраста. Поднимать экспозицию нельзя:
на 11 м/с смаз съест маркер. Это вопрос к освещению арены, а не к коду.

## Что не сделано и почему

- **Синхронизация двух узлов** — есть один модуль. Нужен второй CM4/CM5,
  общий светодиод и прогон `scripts/lan_sync_check.py` на 50 вспышек.
  Без этой цифры задание по ТЗ не закрыто.
- **Светодиодный тест** (`led_timestamp_probe.py`) — светодиод на GPIO не
  подключён. Привязка метки определена развёрткой по экспозиции, но
  `line_time_ns` остаётся из регистровой модели.
- **Гигабитный канал** — стенд на USB-адаптере 100 Мбит/с. Из-за этого
  два окна 480×480 в y8 (306 Мбит/с) на полной частоте не проходят, и все
  замеры сделаны на JPEG-окнах; на гигабите y8 должен проходить.
  Проверить на нормальном LAN, когда будут кабели.
- **Шесть камер одновременно** — оценка только по измеренному объёму
  одного узла.
- **Замер CPU ноутбука при шести камерах** — не делался.
