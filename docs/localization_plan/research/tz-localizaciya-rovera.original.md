# ТЗ: система внешней локализации роверов на ринге 12×12 м

Версия 0.1, черновик для сверки. Часть параметров помечена как **[ПРОВЕРИТЬ]** — они зависят от данных, которых пока нет.

---

## 1. Назначение

Внешняя инфраструктурная система, которая в реальном времени определяет положение и курс собственного ровера и положение ровера противника на ринге и передаёт эти данные в контур автономного управления.

Система инфраструктурная: камеры и вычислитель стоят вне роверов. Бортовая локализация рассматривается только как резервный контур (раздел 13).

**[ПРОВЕРИТЬ]** Правилами соревнования должна быть разрешена установка внешней инфраструктуры над рингом. Без этого ТЗ неприменимо целиком.

## 2. Исходные данные

### 2.1 Ринг

| Параметр | Значение |
|---|---|
| Размер | 12 × 12 м |
| Высота | 3 м |
| Возможная высота подвеса камер | до 2.9 м |
| Монтаж на потолок | **недоступен** |
| Доступные точки монтажа | углы куба и середины рёбер, с регулировкой угла наклона оптики |

### 2.2 Система координат

Правая, начало в углу ринга на уровне пола:
- X, Y — вдоль стен, 0…12 м
- Z — вверх, пол Z = 0
- Курс θ отсчитывается от оси X против часовой стрелки

Вся обработка ведётся в этой системе. Пиксельные координаты существуют только внутри модуля детекции одной камеры.

|---|---|

| Максимальная скорость | **[ПРОВЕРИТЬ]**, расчёты ведутся для 2 м/с |
| Переворот | возможен, должен обрабатываться |

### 2.4 Имеющееся оборудование

6 × сенсор Sony IMX296:
- 1/2.9″, активная область 5.02 × 3.75 мм
- 1456 × 1088, пиксель 3.45 мкм
- глобальный затвор, 60 fps на полном разрешении

**[ПРОВЕРИТЬ]** До проектирования обвязки необходимо уточнить у владельца оборудования:
1. Производитель и точная модель, фото платы с маркировкой
2. Интерфейс: MIPI CSI-2 / USB3 / GigE
3. Байонет: M12 / CS / C
4. Комплектные объективы, фокусные расстояния
5. Наличие выведенной линии внешнего триггера
6. Монохром или цвет (монохром предпочтителен)

Пункты 2 и 3 меняют архитектуру радикально. Пункт 3 критичен: требуемые объективы 2.0–2.2 мм **в байонете CS не существуют** для формата 1/2.9″, нужен M12 или переходник.

## 4. Архитектура

```
[6 × камера] → [детекция на месте] → сеть → [слияние + EKF] → [радиоканал] → [ровер]
                                        ↓
                                   [YOLO на ноутбуке]
```

Три принципа, отступать от которых нельзя:

**4.1 Весь конвейер в мировых координатах.** Перевод из пикселей выполняется в модуле детекции, **до** ассоциации и фильтрации. Причины: слить треки шести камер в пикселях невозможно; модель постоянной скорости в пикселях при широком угле физически неверна; ковариация R в пикселях несравнима между камерами.

**4.2 По сети передаются детекции, а не изображения.** Сшивка изображений в измерительном контуре запрещена: панорама склеивается по гомографии пола и корректно сшивает только пол, а объект высотой 25 см на шве раздваивается или исчезает. Плюс 20–40 мс задержки и потеря субпиксельной точности при ресемплинге. Панорама допустима отдельным потоком для оператора.

**4.3 Каждое измерение несёт таймштамп момента экспозиции.** Обновление фильтра применяется по этому времени, а не по моменту прихода пакета.

## 5. Подсистема камер

### 5.1 Размещение

Гибридная схема: две надирные камеры закрывают центр, четыре наклонные — периметр.

**Центральные (2 шт.), оптическая ось строго вниз:**

| Параметр | Значение |
|---|---|
| Позиции | (4, 6, 2.9) и (8, 6, 2.9) |
| Объектив | 2.0 мм, M12 |
| Пятно на плоскости маркера | 7.53 × 5.62 м |
| Покрываемая зона | полоса Y от 3.2 до 8.8 м по всей ширине X |
| Площадь | ≈ 67 м², включая центр ринга |
| Разрешение | 5.1 мм/пиксель |

**Периметральные (4 шт.), наклон вниз:**

| Параметр | Значение |
|---|---|
| Позиции | (6, 0), (6, 12), (0, 6), (12, 6), высота 2.9 м |
| Объектив | ≈ 2.2 мм, M12 **[ПРОВЕРИТЬ расчётом под фактический байонет]** |
| Зона | пристеночная полоса шириной 3.5 м |
| Максимальная горизонтальная дальность | 6.9 м |
| Минимальный угол места | 21° |

Камеры ставятся в серединах стен, **не в углах**. Угловая камера не видит собственный угол — под ней слепая зона, закрыть её нечем. Камера в середине стены видит свою полосу целиком, включая точку под собой.

### 5.2 Ограничения наклонной схемы

Два эффекта определяют требования к маркерам:

**Разрешение вдоль направления взгляда:** `GSD_вдоль = R · IFOV / sin(γ)`, где γ — угол места. При γ = 21° штраф ×2.8 относительно надира.

**Затенение:** ровер высотой 25 см отбрасывает слепую зону длиной `h / tan(γ)`. При γ = 21° это 0.65 м, при γ = 10° — 1.42 м.

**Требование: угол места в любой рабочей точке ≥ 20°.** Это ограничивает горизонтальную дальность величиной 7.1 м при высоте 2.9 м.

Из этого следует, что **плоский горизонтальный маркер на крыше наклонными камерами не читается** на дальностях свыше ~4 м. Отсюда требование двух типов маркеров (раздел 6).

### 5.3 Запас и риски

В надирной схеме запас по высоте подвеса составлял бы 70 см. В наклонной запаса нет: расчёт по площади покрытия при пороге γ ≥ 20° даёт 318 м² брутто на 144 м² ринга, при пороге γ ≥ 30° — 128 м², то есть уже недостаточно.

**Шести камер в наклонной схеме хватает впритык.** Любое отклонение от проекта (нельзя повесить в задуманной точке, ферма ниже, прожектор бьёт в объектив) создаёт дыру в покрытии. Рекомендация: добыть ещё две камеры.

### 5.4 Требования к оптике и настройкам

- Объектив M12, разрешающая способность не ниже 3 Мп (под пиксель 3.45 мкм), низкая дисторсия, F2.0–F2.8
- **До закупки шести штук проверить резкость по углам кадра** на 2–3 образцах разных производителей. Дешёвый широкоугольный M12 даёт резкий центр и кашу по краям, а на краях у вас стыки камер и максимальные дальности
- Фокусировочные и диафрагменные кольца зафиксировать лаком после настройки
- Выдержка ≤ 2 мс, аналоговое усиление минимальное
- Автоэкспозиция, автобаланс белого, автофокус — **отключить жёстко**. Любое авто ломает калибровку
- Монохром предпочтителен: нет байеровской интерполяции, углы маркера режутся резче, чувствительность выше

## 6. Маркеры

### 6.1 Верхний маркер — для центральных камер

| Параметр | Значение |
|---|---|
| Тип | ChArUco 5×5, словарь DICT_4X4_50 |
| Размер | 600 × 600 мм |
| Размещение | крыша ровера, жёсткая плоская пластина, строго горизонтально |
| Печать | матовая, чёрный обычный (не «богатый») |

Обоснование: субпиксельная локализация углов шахматки точнее углов маркера; доска детектится при потере части поля, что важно при повреждениях в бою; вычислительно дешевле AprilTag. Внутренние ArUco работают запасным вариантом, когда доска целиком не читается.

### 6.2 Нижний маркер — на случай переворота

| Параметр | Значение |
|---|---|
| Тип | ArUco DICT_4X4_50, одиночный |
| Размер | 600 × 600 мм |
| ID | **отличный от верхнего** |
| Защита | утопить на 3–5 мм в нишу, закрыть матовым поликарбонатом |

Разные ID сверху и снизу дают автоматическое определение переворота.

**Требование:** при детекции нижнего маркера система обязана учитывать зеркальность. Перевёрнутый ровер виден в зеркальном отражении: знак курса и направление поворота инвертируются. Заложить в обработку изначально.

### 6.3 Боковые маркеры — для наклонных камер

| Параметр | Значение |
|---|---|
| Тип | ArUco DICT_4X4_50 |
| Размер | 250–300 мм |
| Количество | 4, по одному на каждую грань невысокой мачты |
| ID | четыре разных, дают курс однозначно |

Обоснование: вертикальная площадка при малом угле места почти не ракурсится (укорочение cos 21° = 0.93). Маркер 300 мм на дальности 7 м даёт 38 пикселей, что достаточно для 4×4. Достаточно видимости одной грани.

### 6.4 Почему не AprilTag

AprilTag 36h11 — сетка 8×8 против 6×6 у ArUco 4×4, то есть на треть меньше пикселей на ячейку при том же физическом размере. На наклонных камерах 36h11 даёт ~3.1 пикселя на ячейку и не детектируется. Плюс детекция втрое дороже. Его преимущество (устойчивость к смазу) не окупает потерю разрешения, которое здесь является главным дефицитом.

### 6.5 Резервный вариант при проблемах с освещением

Если на площадке обнаружатся неустранимые блики или засветка: ИК-ретрорефлекторы (3–4 кружка светоотражающей плёнки по углам крыши) + ИК-подсветка на камерах + ИК-фильтр на объективах. Сцена становится чёрной, метки белыми, детекция 1–3 мс, не зависит от освещения. ID отсутствует, свой ровер различается по геометрии созвездия. Для противника не применимо.

## 7. Синхронизация и время

**Ключевое различение: системе нужна не одновременность экспозиции, а точная метка времени каждого кадра.** Фильтр Калмана переваривает асинхронные измерения без потери точности, если у каждого известен свой момент времени. Обратное неверно: при синхронных камерах и неопределённости времени 20 мс на скорости 2 м/с возникает 4 см ошибки.

Требования:

| Требование | Значение |
|---|---|
| Таймштамп момента экспозиции | обязательно, точность ≤ 1 мс |
| Синхронизация времени между узлами | PTP, аппаратные таймштампы |
| Аппаратный триггер | желателен, один генератор на все камеры |
| Частота триггера | 20–60 Гц |
| Передача триггера | дифференциальная (RS-422) или оптика; TTL по витой паре на 12 м поймает наводки |
| Коммутация | управляемый гигабитный свитч, **не потребительский роутер** (непредсказуемая задержка, нет поддержки PTP) |

**[ПРОВЕРИТЬ]** Выведена ли линия внешнего триггера на имеющихся модулях. У Raspberry Pi GS Camera площадка XVS есть, но не распаяна. У модулей InnoMaker и части Arducam триггер поддерживается явно.

## 8. Вычислительная платформа

### 8.1 Распределение нагрузки

| Узел | Задача |
|---|---|
| Вычислитель при камере (CM4) | детекция ArUco/ChArUco, PnP, перевод в мировые координаты, сжатие H.264 для YOLO |
| Центральный (ноутбук, RTX 3070) | YOLO по противнику, слияние, EKF, интерфейсы |

### 8.2 Бюджет вычислений

| Задача | Нагрузка |
|---|---|
| ArUco, 6 камер × 20 Гц | 1.2–1.8 ядра CPU |
| YOLOv8n TensorRT FP16, 6 × 10 Гц, 640 px | ≈ 25 % GPU |
| Итого | запас пятикратный |

Ноутбук с RTX 3070 покрывает задачу с большим запасом. Ограничением является не производительность, а полоса и задержка.

### 8.3 Полоса

Шесть сырых потоков 1456×1088 моно на 20 Гц — 1.5 Гбит/с, гигабит не выдержит.

| Поток | Объём |
|---|---|
| Детекции ArUco (углы + таймштамп) | десятки байт на кадр, пренебрежимо |
| H.264 для YOLO, 6 × 10 Гц | 20–40 Мбит/с суммарно |

У CM4 есть аппаратный H.264-энкодер (у Pi5 его нет) — это аргумент в пользу CM4. Декодирование на ноутбуке через NVDEC.

### 8.4 Оптимизация детекции на CM4

Процессор CM4 (A72 @ 1.5 ГГц) не потянет детекцию на полном кадре в 60 Гц напрямую. Схема:
1. Детекция на кадре, уменьшенном вдвое (728×544)
2. Уточнение углов на полном разрешении через `cornerSubPix` в найденном ROI
3. Со второго кадра — поиск только в предсказанном ROI, полный скан раз в 10–20 кадров

### 8.5 Бюджет задержки

| Этап | мс |
|---|---|
| Экспозиция | 2 |
| Считывание + детекция на CM4 | 15 |
| Сеть | 2 |
| Слияние + EKF | 2 |
| Радиоканал до ровера | 5–20 **[ПРОВЕРИТЬ]** |
| **Итого** | **25–45** |

При 2 м/с это 5–9 см пути, компенсируется в фильтре по таймштампу.

## 9. Калибровка

Самая рискованная часть проекта. Ошибка в 1° по ориентации камеры даёт ~5 см систематического сдвига и «прыжок» ровера при переходе между камерами.

### 9.1 Интринсики

- ChArUco-доска, отдельно для каждой камеры
- Модель `CALIB_RATIONAL_MODEL` — обычной полиномиальной при 2.0–2.2 мм недостаточно
- Целевая ошибка репроекции < 0.3 px
- Undistort применяется **до** детекции маркеров

### 9.2 Экстринсики в единой системе координат ринга

Основной способ: крупные ArUco-маркеры разложены по полу в узлах известной сетки, сняты всеми камерами, глобальный bundle adjustment по со-видимым маркерам.

Альтернатива без разметки пола: прокатить ровер с маркером по всему рингу, связать позы камер через со-наблюдения, оптимизировать глобально.

### 9.3 Верификация

Обязательный приёмочный тест: маркер ставится в N известных точек (не менее 20, включая стыки зон камер), измеряется ошибка. **Критерий приёмки: ≤ 2 см в центральной зоне, ≤ 5 см на периметре, отсутствие скачка > 2 см при переходе между камерами.**

### 9.4 Повторяемость

Система перекалибровывается после каждой перевозки/переустановки. Процедура должна быть документирована и выполнима силами одного человека за ≤ 1 час.

## 10. Алгоритмы: свой ровер

### 10.1 Детекция

| Шаг | Требование |
|---|---|
| Undistort | обязательно, до детекции |
| Детекция | ChArUco (верх) / ArUco (низ, борта) |
| Поза | `solvePnP`, флаг `SOLVEPNP_IPPE_SQUARE` |
| Перевод | в мировые координаты через экстринсики |

**Обязательно использовать solvePnP, а не центр маркера.** Полная 6-DoF поза автоматически учитывает, что маркер находится на высоте 0.25–0.3 м над полом. Гомография пола эту ошибку не исправляет: при наклонной камере на краю зоны параллаксная ошибка достигает 30 см.

### 10.2 Ассоциация

**ArUco/ChArUco ассоциируется по ID напрямую, минуя матрицу стоимостей и венгерский алгоритм.** У маркера уникальный ID, смены идентификатора для маркерного объекта не должно происходить в принципе. Прогон маркерных детекций через общий ассоциатор — архитектурная ошибка.

### 10.3 Фильтрация

| Параметр | Значение |
|---|---|
| Состояние | [x, y, θ, v, ω] в мировых координатах |
| Тип | EKF или UKF |
| Входы | детекции с камер (20 Гц), одометрия колёс, гироскоп IMU (200 Гц) |
| Выход | 100–200 Гц |
| Обработка запаздывающих измерений | out-of-sequence update по таймштампу, либо буфер управляющих воздействий с перепрогоном |
| Δt | по реальному таймштампу, **не по индексу кадра** |

Взвешивание детекций от разных камер: по площади маркера в кадре, удалению от центра кадра и углу места. Ковариация R задаётся **в метрах**.

### 10.4 Слияние нескольких камер

В зонах перекрытия один маркер виден двумя камерами. Измерения не усредняются на уровне пикселей — каждое подаётся в фильтр как независимое со своей R.

## 11. Алгоритмы: ровер противника

### 11.1 Детекция

| Параметр | Значение |
|---|---|
| Модель | YOLOv8n или YOLO11n, дообученная на своих данных |
| Инференс | TensorRT FP16 |
| Разрешение входа | 640 px |
| Порог confidence | **0.25–0.35** |
| Датасет | 500–2000 размеченных кадров с фактической установки |

**Порог 0.7 (как в наследуемом коде) недопустим** — он душит recall, а от ложных срабатываний защищает гейтинг по Махаланобису. Пусть трекер отсеивает, а не детектор.

Разметка датасета: использовать SAM (MobileSAM / EfficientViT-SAM) для полуавтоматической генерации масок. **SAM только на этапе подготовки данных, не в рантайме** — он класс-агностичен, требует промпта и на два порядка тяжелее бюджета.

### 11.2 Перевод в координаты

Ровер не плоский, высота 25 см. Центр рамки брать нельзя: параллаксная ошибка при наклонной камере на краю зоны до 30 см.

Порядок предпочтения:
1. **Подгонка 3D-параллелепипеда 900×700×250 мм под видимый контур** — габариты известны точно, даёт центр, курс и устойчивость к частичному перекрытию
2. Триангуляция по двум камерам в зоне перекрытия
3. Нижняя точка контакта с полом через гомографию пола

### 11.3 Трекинг

- В кадре: ByteTrack
- В мировых координатах: ассоциация детекций со всех камер венгерским алгоритмом, Kalman с моделью постоянной скорости
- При двух и более противниках: JPDA, иначе треки слипаются при сближении

### 11.4 MOG2

**Вычитание фона не заводится в контур измерений.** Обоснование: в наследуемой работе именно сценарии с доминированием MOG2 дали максимум ложных треков (6 и 8 против 1 у маркерного канала). На ринге условия хуже: искры, отлетающие детали, дым, тени от двух движущихся объектов, вращающееся оружие.

Допустимое применение: отдельный индикатор «в зоне движение, не объяснённое известными треками» — для оператора и аварийной логики. Треки не создаёт.

## 12. Жизненный цикл треков

| Состояние | Переход |
|---|---|
| tentative | создаётся несопоставленным измерением |
| confirmed | после N успешных обновлений подряд |
| lost | нет подтверждений M кадров, состояние удерживается прогнозом, P растёт |
| удалён | нет подтверждений K кадров |

Гейтинг по расстоянию Махаланобиса, порог по χ² для двумерного измерения. Пороги N, M, K подбираются по размеченным данным, не вручную.

## 13. Резервный контур и отказоустойчивость

| Отказ | Реакция |
|---|---|
| Потеря маркера < 200 мс | прогноз EKF |
| Потеря локализации 0.2–5 с | бортовая одометрия + IMU |
| Потеря > 5 с | аварийная остановка |
| Отказ одной камеры | деградация покрытия, система продолжает работу, оператор уведомляется |
| Отказ радиоканала | аварийная остановка по таймауту на борту |

Бортовой резерв (минимум): колёсная одометрия + IMU. Опционально: 2D-лидар с AMCL по карте ринга (3–5 см) или UWB-якоря в углах (10–30 см).

## 14. Интерфейсы

- ROS2, отдельные топики для своего ровера и ровера противника
- Формат измерения: `(camera_id, source, world_point, timestamp, R, attributes)`
- Формат трека: `(id, состояние, ковариация, статус, timestamp, источник последнего обновления)`
- Журнал: покадровое сохранение всех измерений и треков для разбора и обучения
- GUI оператора: визуализация треков, включение/отключение отдельных камер и каналов, индикация статуса трека цветом

## 20. Ключевые решения, принятые в этом ТЗ

Для быстрой сверки — список того, что было выбрано осознанно и с обоснованием:

1. Мировые координаты вместо пиксельных на всём конвейере
2. Детекции по сети вместо сшитого изображения
3. Таймштамп важнее синхронности экспозиции
4. Гибридная схема: 2 надирные + 4 наклонные вместо равномерной сетки
5. Камеры в серединах стен, не в углах
6. Угол места ≥ 20° как жёсткое ограничение
7. Три типа маркеров: ChArUco сверху, ArUco снизу, вертикальные ArUco по бортам
8. ArUco 4×4 вместо AprilTag 36h11 — разрешение важнее устойчивости к смазу
9. MOG2 выведен из контура измерений
10. Порог YOLO снижен с 0.7 до 0.25–0.35
11. solvePnP вместо центра маркера
12. ArUco ассоциируется по ID, а не венгерским алгоритмом
