# План системы локализации двух роверов

Пакет для последовательной реализации в этом репозитории. Это проект требований
и промпты для разработки, а не уже работающая система одометрии.

Основной результат: визуальная одометрия своего ровера с AprilTag 36h11
на 20–30 Гц и оценка движения второго ровера без метки на ≥10 Гц,
панель шести камер IMX296, калибровка, синхронизация и диагностика.
Под «вражеским» здесь понимается второй робот на арене; управление оружием,
наведение и автономные боевые действия в задачу не входят.

## Параллельное исследование

[Согласование исследования и изменений ТЗ](05_research_integration.md) содержит
матрицу решений, исправления расчётов и обязательные SIM-эксперименты.
[Исходный черновик](research/tz-localizaciya-rovera.original.md) сохранён без изменений.
Он является материалом исследования, а не самостоятельной инструкцией агенту.
Перед каждым этапом читать согласование вместе с требованиями; спорные тезисы
не заменяют исходный AprilTag и заданные частоты без результатов сравнения.

## Порядок работы: сначала вся система в симуляторе

**Фаза 1: S01–S15, только Gazebo и replay.** Должны работать оба оценивателя,
калибровка по изображениям, панель настроек и диагностики, запись, воспроизведение
и нагрузочные проверки. Реальные камеры и драйверы для этого не требуются.

**Фаза 2: H01–H04, оборудование.** Начинается после успешной SIM-приёмки и
отдельного запроса пользователя. Здесь появляются драйверы IMX296, libcamera,
udev, узлы захвата, аппаратный trigger, реальные калибровки и перенос YOLO.

1. Прочитать [требования](01_requirements.md), [архитектуру](02_architecture.md)
   и [дорожную карту с критериями](04_implementation_plan.md).
2. В новой сессии передать [общий контекст](prompts/00_context.md) и один S-промпт.
3. Выполнять S01 → S15, без перехода к H-промптам между ними.
4. После каждого этапа обновлять `STATUS.md`: фаза, ID этапа, сделано,
   проверено, команды, метрики, ограничения, следующий файл.
5. S15 формирует `sim_acceptance_report.md`. Только при прохождении обязательных
   SIM-критериев выставляется `SIM_ACCEPTED`. Провалы исправляются в S-этапах.
6. После SIM_ACCEPTED можно отдельно начать H01. Отсутствие аппаратуры не
   мешает завершить фазу симуляции. Неизвестное железо — в `hardware_backlog.md`.

Отчёты STATUS.md и acceptance reports создаются при реализации; сейчас план
не утверждает, что этапы выполнены. [Аппаратный справочник](03_cameras_and_calibration.md)
сохранён для будущей фазы, его пункты не являются текущими заданиями.

## Главные решения

- Публикация 30 Гц не означает 30 новых измерений в секунду. Показывать обе частоты.
- Текущий симулятор выдаёт 15 кадров/с на камеру; это надо изменить и измерить
  реальное время, прежде чем заявлять выполнение 20–30 Гц по новым наблюдениям.
- Оценки состояния публикуются регулярно, измерения принимаются асинхронно по
  времени экспозиции. Не ждать все шесть камер ради каждого обновления ровера.
- Экран настройки и видео не должны задерживать одометрию.
- Фокусное расстояние в мм — описание объектива, а не замена измеренной K/D.
- Пользователь уточнил модель ссылкой на Arducam: выбран CSI-вариант.
  Конкретные SKU/ревизия, узлы захвата, объективы и trigger требуют проверки;
  подробнее — в документе 03. Udev не заменяет идентификацию в libcamera.

Все численные пороги точности и задержки ниже — исходные проектные цели,
их ещё нужно подтвердить измерениями. Частоты 20–30 Гц и ≥10 Гц — запрос пользователя.
