# Стенд, второй заход: потери на camera_2/4/6, схема с одним окном, малый поток в JPEG, кодер H.264

Для коллег на стенде из шести CM4. Продолжение отчёта от 04.10.2026
(`SUMMARY.md`, прогоны S1–S5, B, C). Спасибо за тот прогон: он очень
аккуратный, и по нему видно, что делать дальше.

## Что мы поняли из первого захода

1. **CM4 справляются.** Сенсор не пропустил ни одного кадра, CPU до 32 %,
   температура до 55 °C, уменьшение кадра около 8 мс. Узлы не виноваты.
2. **Потери почти целиком на camera_2, camera_4, camera_6.** Так было в S3, S4, C
   и даже в S5. Повторные передачи TCP тоже только у них. В S3 у camera_4 и
   camera_6 окон не было вообще, только малый поток, и они всё равно теряли кадры.
   Значит, дело не в нагрузке на узел, а в чём-то общем для этих трёх: порты
   коммутатора, кабели, сплиттеры или сами платы. Это главный вопрос захода.
3. **S3 проверял не ту схему — это ошибка в нашем задании.** Инструмент по
   умолчанию шлёт **два** окна на узел (старая схема: окно на каждый ровер).
   В целевой схеме окно **одно** (только наш ровер). Поэтому вышло 850 Мбит/с
   вместо примерно 650. Окно теперь задаётся явно: `--windows "376,580,320,320"`.
4. **Малый поток задерживает окна на 5.6 мс (S1 → S2).** Окна и малые кадры
   идут через один TCP-сокет, и окно ждёт, пока уйдёт кадр 307 КБ. Проверяем
   малый поток в JPEG: кадр уже серый (усреднение 2×2), мозаики Байера в нём
   нет, а объём должен упасть в 5–8 раз.

## Общие правила (как в прошлый раз)

- **Код и конфиги узлов не менять.** На узлах остаётся тот же код, что был
  (`6fcb0ad`). Все нужные флаги в нём уже есть. Ноутбук — тот же коммит или новее.
- Обновлять узлы не нужно. Исключение — пункт 1.5 (EEE), он временный и
  отменяется перезагрузкой.
- Перед каждым прогоном PTP в состоянии READY (camera_1 MASTER, остальные
  SLAVE, смещение ноутбука < 10 мкс), как вы делали.
- Если в статусе узла висит `send: [Errno 9] Bad file descriptor`, это,
  скорее всего, след от прошлого отключения клиента: поле `last_error` в узле
  не очищается. Записать в отчёт и перезапустить `camera_node` на этом узле —
  это разрешено.
- Сохранять всё, как в прошлый раз: `--json` каждого прогона, полный текстовый
  вывод, снимки «до/после». Каталог `artifacts/field_<дата>/`.
- Не запускать два `lan_camera_timing.py` одновременно. Во время прогонов
  `iperf3` (этап 1) `lan_camera_timing.py` не запущен.

OUT=artifacts/field_$(date +%Y%m%d)_r2

### Снимок сетевых счётчиков (до и после каждого прогона)

Этот снимок нужен в каждом прогоне: по нему видно, где теряются пакеты.

```bash
snap() {  # snap <имя>, например snap C_before
  {
    echo "=== laptop $IFACE"; ethtool -S $IFACE | grep -iE "err|drop|crc|miss|over|pause|xon|xoff"
    ip -s link show $IFACE
    for i in 1 2 3 4 5 6; do
      echo "=== camera_$i"
      ssh pi@192.168.10.10$i 'ethtool -S eth0 | grep -iE "err|drop|crc|fcs|discard|over|miss"; ip -s link show eth0; vcgencmd get_throttled'
    done
  } > $OUT/$1.txt 2>&1
}
```

## Этап 1. Сеть без нашего кода: iperf3 (≈ 30 мин)

Цель — понять, теряет ли пакеты сама сеть, независимо от узла камеры.
Служба `camera_node` может работать: без подключённого клиента она ничего не
шлёт.

Установка (если на узлах нет интернета — пропустить этап и написать об этом):

```bash
sudo DEBIAN_FRONTEND=noninteractive apt install -y iperf3   # на ноутбуке и на каждом узле
```

На ноутбуке — шесть серверов, по порту на камеру:

```bash
for i in 1 2 3 4 5 6; do iperf3 -s -p 520$i -D; done
```

**1.1. Каждый узел по одному, TCP, 30 с.** По очереди, не одновременно:

```bash
snap I1_before
for i in 1 2 3 4 5 6; do
  ssh pi@192.168.10.10$i "iperf3 -c 192.168.10.1 -p 520$i -t 30 -J" > $OUT/I1_cam$i.json
done
snap I1_after
```

Ждём около 940 Мбит/с и `retransmits` ≈ 0 на каждом. Если у одного узла уже
здесь повторные передачи, проблема в его линии (кабель, порт, сплиттер, плата),
а не в одновременной нагрузке.

**1.2. Все шесть одновременно, TCP, по 70 Мбит/с (всего 420), 60 с:**

```bash
snap I2_before
for i in 1 2 3 4 5 6; do
  ssh pi@192.168.10.10$i "iperf3 -c 192.168.10.1 -p 520$i -t 60 -b 70M -J" > $OUT/I2_cam$i.json &
done; wait
snap I2_after
```

**1.3. То же по 130 Мбит/с (всего 780).** Повторить 1.2 с `-b 130M`, имена
`I3_*`.

**1.4. UDP по 130 Мбит/с, все шесть.** Показывает прямые потери пакетов без
повторных передач TCP:

```bash
snap I4_before
for i in 1 2 3 4 5 6; do
  ssh pi@192.168.10.10$i "iperf3 -c 192.168.10.1 -p 520$i -t 30 -u -b 130M -l 1400 -J" > $OUT/I4_cam$i.json &
done; wait
snap I4_after
```

В отчёт — таблица по камерам: Мбит/с, `retransmits` (TCP), `lost_percent`
(UDP) для 1.1–1.4.

**1.5. Только если в 1.2–1.4 снова выделяются camera_2/4/6 и на них включён
EEE.** Временно выключить EEE на всех шести узлах (действует до перезагрузки):

```bash
for i in 1 2 3 4 5 6; do ssh pi@192.168.10.10$i "sudo ethtool --set-eee eth0 eee off"; done
```

Повторить 1.3 и 1.4 (имена `I3_eeeoff_*`, `I4_eeeoff_*`). Записать, помогло
ли. Перед этапом 3 вернуть как было (перезагрузить узлы или `eee on`) и
написать в отчёте, в каком состоянии шли дальнейшие прогоны.

## Этап 2. Где именно проблема: перестановки (≈ 45 мин)

Нагрузка для проверки — прогон C из прошлого раза: он за 120 с надёжно
воспроизводил потери на camera_2/4/6 (1558 сброшенных окон).

```bash
c_run() {  # c_run <имя>
  snap $1_before
  .venv/bin/python scripts/lan_camera_timing.py --nodes $N --seconds 120 \
    --window-size 320 --window-format y8 --full-period 0 --clock-mode ptp \
    --json $OUT/$1.json | tee $OUT/$1.txt
  snap $1_after
}
```

**2.0. Повтор C без перестановок:** `c_run C0`. Проверяем, что картина та же:
потери на 2/4/6.

Дальше перестановки. Всё переключать при выключенном питании узлов
(PoE с этих портов можно снять, вынув кабель). После каждой перестановки —
PTP READY, затем прогон. Дальше в 2.1–2.3 «линия» означает порт коммутатора,
кабель и сплиттер.

**2.1. Поменять местами порты коммутатора** у camera_1 и camera_2. Кабели и
сплиттеры остаются при своих узлах, меняются только гнёзда на коммутаторе.
Прогон `c_run C_swapport`.

**2.2. Вернуть порты. Поменять кабели целиком** у camera_1 и camera_2.
Прогон `c_run C_swapcable`.

**2.3. Вернуть кабели. Поменять сплиттеры** у camera_1 и camera_2.
Прогон `c_run C_swapsplit`.

Как читать:

| Где оказались потери после перестановки | Виновник |
|---|---|
| ушли вместе с портом на camera_1 (2.1) | порт или группа портов коммутатора |
| ушли вместе с кабелем (2.2) | кабель |
| ушли вместе со сплиттером (2.3) | сплиттер / питание |
| остались на camera_2 во всех трёх | сам узел (CM4, плата CM4-NANO-B) |
| пропали совсем после любой перестановки | плохой контакт в разъёме; переобжать / заменить |

Если виновник найден и его можно заменить (свободный порт, запасной кабель,
другой сплиттер), заменить для **всех трёх** проблемных камер и повторить
`c_run C_fixed`. Дальше этапы 3–4 идти уже на исправленной схеме и записать,
что именно поменяли.

Если перестановки ничего не дали (потери на 2/4/6 при любом раскладе), всё
равно перейти к этапам 3–4. Это тоже важный результат.

## Этап 5. Аппаратный кодер H.264 на одном CM4 (≈ 20 мин)

Отдельный вопрос, сеть здесь не участвует. Мы думаем передавать малый поток
(а может быть, и запись полных кадров) в H.264 на аппаратном кодере CM4.
Пробник `pi_cam/h264_probe.py` читает сенсор так же, как узел, готовит кадр
(уменьшение до 640×480 или полный кадр в сером), кодирует его аппаратным
кодером и измеряет каждый шаг. Сеть и ноутбук не нужны, всё происходит на
одном узле. Код узла не меняется: пробник кладётся в `/tmp` и работает рядом.

Делать на **camera_5** (любой узел подойдёт, этот не участвует в окнах).
Этап можно делать в любой момент, когда не идёт `lan_camera_timing.py`, но
не во время этапов 1–4: на время пробника служба камеры на узле остановлена.

Если в вашем клоне репозитория нет `pi_cam/h264_probe.py`, он приложен к
заданию: положите его в `pi_cam/`.

На ноутбуке:

```bash
scp pi_cam/h264_probe.py pi@192.168.10.105:/tmp/
ssh pi@192.168.10.105
```

На узле:

```bash
cat /sys/class/video4linux/video11/name      # ждём bcm2835-codec-encode
sudo systemctl stop camera_node
cd /tmp
```

**5.1. Неподвижная сцена** (≈ 2.5 мин: четыре случая по 30 с). В кадре
ничего не двигается:

```bash
PYTHONPATH=/opt/mocap-rover python3 h264_probe.py --config /etc/mocap-rover/node_config.json \
  --exposure-us 3000 --seconds 30 --save-dir h264_static \
  --output h264_static.json | tee h264_static.txt
```

Экспозиция 3 мс нужна, чтобы кадр не был чёрным: на чёрном кадре H.264 почти
ничего не весит, и размеры будут нереалистичные.

**5.2. Сцена с движением.** Та же команда с именами `h264_motion`. Всё время
прогона кто-то двигает под камерой крупный предмет (коробку, ровер в руках),
лучше быстро и по всему кадру. Это худший случай по размеру кадров.

**5.3. Малый битрейт** (≈ 1.5 мин), с движением, как в 5.2:

```bash
PYTHONPATH=/opt/mocap-rover python3 h264_probe.py --config /etc/mocap-rover/node_config.json \
  --exposure-us 3000 --seconds 30 --cases 640x480@all 640x480@30 --bitrate-small 4 \
  --save-dir h264_4mbit --output h264_4mbit.json | tee h264_4mbit.txt
```

После прогонов:

```bash
sudo systemctl start camera_node
journalctl -u camera_node -n 5          # ждём Selected sensor format: 1640x1232-SBGGR8_1X8
```

На ноутбуке забрать всё (сохранённые потоки — около 100 МБ):

```bash
scp -r 'pi@192.168.10.105:/tmp/h264_*' $OUT/
```

Что прогоняется по умолчанию: `640x480@all` (каждый кадр сенсора, 83 Гц),
`640x480@30`, `full@30` (1640×1232) и `full@all` (полный кадр на каждом кадре
сенсора; кодер, скорее всего, не успеет, и это покажет его потолок).

Что смотреть в выводе для каждого случая:

| Строка | Что значит |
|---|---|
| `hold test … no hold` / `HOLDS A FRAME` | **главное**: отдаёт ли кодер кадр сразу или держит до прихода следующего (тогда к задержке добавляется период кадра: 12 мс при 83 Гц, 33 мс при 30 Гц) |
| `rate in … out …`, `encoder busy` | успевает ли кодер: `out` ≈ `in` и `busy` ≈ 0. В `full@all` `out` — это потолок кодера на полном кадре |
| `encoder` P50/P95 | время самого кодера, мс |
| `total_exposure_to_encoded` P95 | от начала экспозиции до готового кадра H.264, мс |
| `size` | размер кадров (P-кадр и опорный) и итоговые Мбит/с |
| `frames … missed` | пропуски сенсора: если не 0, узел не успевает читать камеру |
| `board CPU`, `temp`, `throttled` | загрузка CM4 и нагрев |

Если пробник пишет `no V4L2 H.264 encoder found` — прислать вывод
`ls -l /dev/video*` и `cat /sys/class/video4linux/video*/name`, и попробовать
`--device /dev/video11`. Если какой-то случай упал с `ERROR`, остальные всё
равно выполнятся; прислать вывод целиком.

## Критерии

Для S3b, S3j (и для C после исправления, кроме строк про малый поток):

| Что | Где в выводе | Порог |
|---|---|---|
| сенсор не теряет кадры | `node missed` | 0 |
| окна не сбрасываются узлом | `node dropped` (queue) | 0; единицы в первые секунды допустимы, отметить |
| задержка окон | `window latency` P95 | ≤ 35 мс на каждой камере |
| влияние малого потока на окна | S2b / S2j против S1b | прирост P95 ≤ 2 мс (для информации: в S2 было +5.6) |
| малый поток идёт | `small stream` к/с | 29.5–30.5 на каждой камере |
| малый поток не теряется | `node skipped`, small laptop dropped | ≈ 0 |
| задержка малого кадра | `small latency` P95 | ≤ 50 мс |
| уменьшение (и JPEG) на узле | `node reduce` P95 | ≤ 10 мс в S3b; в S3j записать, сколько вышло |
| CPU узла | P95 | ≤ 70 % |
| температура | max, `throttled` | < 75 °C, none |
| сеть | счётчики `snap` после − до | ошибки и сбросы на интерфейсах = 0 |

Отдельно записать для S3j: **Мбит/с малого потока** на камеру (строка
`small stream`) — нам нужен реальный размер JPEG-кадра на сцене арены.
