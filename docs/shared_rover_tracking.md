# Общий тракт двух роверов (замена `hybrid_rover_tracking.md`)

Один тракт для tag_rover и соперника: **прогноз → окно → измерение → IMM-фильтр**.
Маркер — надстройка идентичности, а не отдельный конвейер. Всё ниже измерено
реплеем (`scripts/replay_dataset.py`) на Gazebo-датасетах IMX219:
`dataset_imx219_01` (seed 7, на нём подбиралось) и отложенном `dataset_imx219_03`
(seed 11, на нём только проверялось).

## Схема

```
главный процесс (один владелец фильтров)          процесс камеры ×6 (CameraWorker)
------------------------------------------         ----------------------------------
IMM tag_rover, IMM opponent                         кадр: DatasetFrameSource | LAN (CameraFrame)
state_at(t): прогноз копии, фильтр не двигается     планировщик окна маркера (CameraRoiPlanner)
позы треков + флаги  ───────── контекст ─────────►  планировщик окна соперника, вырезки корпусов
                                                    детектор AprilTag в окне → PnP / луч-плоскость
                                                    фон ClipBackground → силуэт → extent
                                                    KLT-продолжение, обновление фона вне окон
измерения ◄──────────── результат ────────────────  (пиксели через границу процесса не идут)
AsyncObservationBuffer (окно группы 12 мс)
лидар: ArenaLidar, фон по лучам, кластер в гейте,
  корпус другого ровера вырезан
TwoRoverIdentity: сближения < 1 м, обмен треков по маркеру
публикация 200 Гц
```

Результаты камер применяются в фильтр в порядке камер, поэтому `--parallel
processes|threads|inline` дают побитно одинаковую одометрию (тест
`test_threads_processes_and_one_thread_give_the_same_output`).

## Чем различаются роверы

| | tag_rover | opponent |
|---|---|---|
| создание трека / идентичность | маркер 36h11 ID 0/1 | прямоугольник оператора один раз |
| измерение в камере | маркер: луч-плоскость на высоте метки | силуэт: середина габарита на плоскости половины высоты |
| окно | цель — метка 0.4 м, 160–480 px | цель — корпус 0.9 м, 240–900 px |
| yaw | из маркера, публикуется | ось пятна ±180°, не публикуется |
| лидар | верхний слой 3 см, высота ≤ 0.45 м | верхний слой 0.14 м, высота ≤ 0.55 м |
| продолжение | лидар | KLT, лидар |

**Отложенный эпизод на 03 (t = 99.07–99.39 с, 0.33 с, до 0.40 м при valid).**
camera_5 смотрит под углом 59° и даёт смещение 0.25–0.3 м вдоль луча, в пределах своей σ
(0.17 м). Фильтр его принимает и сжимает P, после чего точные camera_6/camera_4
(1–4 см) и лидар (7 см) не проходят χ²-гейт. Трек возвращается, когда три камеры
сходятся. Лечится учётом корреляции смещения одной камеры или сбросом при
согласии других камер против трека.

## Задержка

Возраст последнего измерения, P50/P95 в мс:

| транспорт | 01 tag | 01 opp | 03 tag | 03 opp |
|---|---|---|---|---|
| 5 мс | 17/23 | 17/23 | 17/23 | 17/24 |
| 15 мс | 20/26 | 20/26 | 20/26 | 21/27 |
| 30 мс | 35/41 | 35/41 | 35/41 | 36/42 |

Разложение: возраст = транспорт + ожидание закрытия группы + фаза публикации.
- **Ожидание группы.** Группа закрывается через 12 мс после экспозиции, поэтому при
  транспорте меньше 12 мс измерение ждёт до 12 мс, а при большем — не ждёт.
- **Фаза публикации.** Кадры синхронны и идут каждые ~12 мс, тик 5 мс, поэтому
  возраст к следующему кадру растёт ещё на 0–12 мс.

При транспорте 5 мс измерение становится доступно через 12 мс после экспозиции,
до следующего добавляется до 12 мс, отсюда P95 23 мс. Критерий ≤ 25 мс
выполняется.

## Производительность (этот ноутбук, Core Ultra 7 155H, датасет 01)

Абсолютные миллисекунды здесь не критерий. Ноутбук ограничен по мощности:
чем больше одновременной работы, тем ниже частота, поэтому упреждающее
декодирование (`--prefetch`) и закрепление ядер (`--pin-cpus`) тут не помогают.
Таблица «процессы / потоки / однопоточно» — в отчёте промпта 04.

Цена кадра по стадиям (процессы): декодирование FFV1 ~6.7 мс, силуэт ~4.3 мс,
передний план ~2.9 мс, детектор ~1.7 мс, gain ~1.1 мс, PnP ~0.8 мс,
обновление фона ~0.4 мс. Главный поток на момент: планирование ~1 мс,
применение ~1.8 мс, публикация фильтра ~3.6 мс на тик.

## Поправка по строке

`--line-time-ns` сдвигает метку времени измерения на `row × line_time`.
- **Синтетика** (ровер 4 м/с, строка 9.5 мкс, `tests/test_apriltag.py`): с
  поправкой ошибка 0.6 мм, без неё 14 мм.
- **Gazebo** (глобальный затвор) с `--line-time-ns 9500`: P95 tag_rover ухудшается —
  01: 15.7 → 27.7 мм, 03: 12.4 → 22.4 мм. Включать только на реальном IMX219.

## Деградированные конфигурации

Пороги: P95 ≤ 0.25 м, valid ≥ 90 %, подмен 0.

| конфигурация | 01 tag P95 / valid | 01 opp P95 / valid | 03 tag P95 / valid | 03 opp P95 / valid | подмены |

| `--cameras camera_3,camera_4` (надир) | 38 мм / 99.98 % | 192 мм / 99.95 % | 27 мм / 99.98 % | 198 мм / 99.91 % | 0 |
| `--cameras camera_1,camera_3,camera_5` | 40 мм / **75.9 %** | **326 мм** / 99.95 % | 35 мм / **72.4 %** | **265 мм** / 99.94 % | 0 |

Вариант 1,3,5 не проходит: при трёх камерах с одной стороны арены маркер
видно реже, идентичность tag_rover устаревает (2 с), трек уходит в REACQUIRING.

## Что ждёт RTX-машины и железа

- Абсолютное время кадра ≤ 5 мс и нагрузка CPU ≤ 60 % на 6 потоках.
- CUDA-вариант модели фона против CPU в окнах.
- Датасет со сдвинутыми фазами камер: возраст при транспорте 15 мс.
- `LanFrame` серый (y8), а модель фона трёхканальная: для живых камер нужна
  одноканальная `ClipBackground`.
- Дефекты `scripts/run_localization.py`: `state` пишется без `stamp_ns` (оценщик
  на живой записи падает). После `874df0b` его `f.x` — состояние на момент
  последнего измерения, а не последнего тика; для окон нужен `f.state_at(now)`.
- Посекторная обработка лидара (gpu_lidar Gazebo рендерит оборот мгновенно).
- Абсолютные пути `/home/popka/...` к мешам лидара в
  `worlds/mocap_arena_imx219.sdf`.
- `scripts/check_dataset.py` падает (`KeyError: 'tag_rover'`) на пустом эталоне.
- Подбор порога фона (`--background-threshold`) на реальной записи с шумом сенсора.
