# Стенд: шесть камер на C++-узле, один поток H.264 (основной сценарий)

Для коллег на стенде из шести CM4. Это **основная схема системы**: каждая
камера шлёт весь кадр 1640×1232 в аппаратном H.264, 50 к/с, около
15 Мбит/с; ноутбук принимает и раскодирует всё на C++. Окна и малый поток
больше не используются (они остаются запасным вариантом). Почему так —
`docs/camera_scenarios.md`.

На одной CM4 уже измерено: 50 к/с без потерь, от начала экспозиции до
раскодированного кадра на ноутбуке **P50 49 мс, P95 56 мс**, CPU узла
около 70 %, 61 °C. Теперь нужно то же на шести камерах, долго, с PTP и
на настоящем свете.

## Что нужно

- Ветка `field/round2-h264` (или `main`, когда в неё вольют) на ноутбуке
  и на каждом узле.
- Один коммутатор: все шесть камер, лидар и ноутбук включены в него.
- Ноутбук: Ubuntu 24.04, гигабитный порт.

## 0. Сеть

**Схема — один коммутатор, ноутбук одним кабелем:**

```
ноутбук 192.168.10.1 ── коммутатор ── cam-1 … cam-6 (192.168.10.101…106), лидар Airy
```

Шесть камер по H.264 — это до 90 Мбит/с, с лидаром около 110 Мбит/с: гигабитный
порт ноутбука загружен примерно на 10 %. Одна подсеть, адреса узлов прежние.

Запишите в отчёт: какая камера в каком порту коммутатора, модель коммутатора
(фото наклейки).

## 1. Ноутбук

```bash
git fetch && git checkout field/round2-h264 && git pull
scripts/hardware/setup_laptop.sh --iface <порт к коммутатору>
```

Скрипт ставит `cmake libavcodec-dev libavutil-dev` и собирает `cpp/build/mocap_rx`.
Проверка: `ls cpp/build/mocap_rx cpp/build/mocap_camstat` — оба файла есть.

## 2. Каждый из шести узлов

На узле, в клоне репозитория (та же ветка):

```bash
git fetch && git checkout field/round2-h264 && git pull
sudo scripts/hardware/setup_cm4_node.sh N --cpp      # N = 1…6
sudo reboot
```

Что делает `--cpp`: собирает C++-узел на плате (около 5 минут), ставит
`/usr/local/bin/mocap_camd`, пишет `/etc/mocap-rover/camd.json` (если его нет),
включает службу `mocap_camd` и выключает Python-узел `camera_node`. Вдвоём
они камеру не делят.

После перезагрузки:

```bash
systemctl is-active mocap_camd ptp4l phc2sys        # три раза active
journalctl -u mocap_camd -n 10                      # 'camera 1640x1232 SBGGR8 via unicam', 'web page on :8080'
sudo pmc -u -b 0 'GET PORT_DATA_SET' | grep portState   # MASTER на camera_1, SLAVE на остальных
```

Скрипт отключает на узле `systemd-timesyncd`: часами управляет только PTP.
Проверено на стендовой CM4: с NTP часы гуляли на миллисекунды. Узел после
холодной перезагрузки стартует сам: в журнале должно быть `rotated 180 (flips on)`.

Откройте в браузере `http://192.168.10.10N:8080`: должна быть живая картинка,
внизу справа в «PTP» — `SLAVE` и смещение в единицы мкс (у camera_1 —
`MASTER`).

**Калибровка** пока идёт через Python-узел. На время калибровки:
`sudo systemctl stop mocap_camd; sudo systemctl start camera_node`, после неё —
обратно.

## 3. Свет и экспозиция (на арене, по каждой камере)

На странице узла `http://<узел>:8080`:

1. Включите рабочий свет арены. Положите в поле камеры маркер (или лист с
   ArUco) и белый лист.
2. Выдержку держите **≤ 1000 мкс**. Рядом показан смаз при 11 м/с: при
   800 мкс это 8.8 мм. Яркость добирайте **усилением**.
3. Выделите мышью маркер. Цель: **пересвет 0 %**, P95 около 200–235,
   контраст как можно выше. Потом выделите пол арены: среднее около 80–150.
4. Если будете проверять цвет: включите «Цвет», выделите белый лист и
   нажмите «Баланс белого по области».
5. Нажмите «Сохранить в конфиг». Узел запомнит настройки после перезапуска.

Запишите в отчёт по каждой камере итоговые выдержку, усиление и
баланс, а также среднее и P95 на маркере и на полу. Приложите снимок экрана
страницы одной камеры.

## 4. Прогоны

Все команды — на ноутбуке, из корня репозитория. По умолчанию узлы
`192.168.10.101…106:5600`. Перед каждым прогоном все шесть узлов в PTP
должны быть `SLAVE`/`MASTER`.

Узел отдаёт поток одному приёмнику: не запускайте два `rx…` одновременно.
Смотреть все камеры во время прогона можно в соседнем терминале:
`scripts/hardware/run_hardware.sh wall`, затем `http://localhost:8090`. Стена
читает кадры из общей памяти, которую пишет идущий `rx-check` или `rx-record`.

| № | Что | Команда | Длительность |
|---|---|---|---|
| A | каждый узел по одному | `NODES="192.168.10.10N:5600" PTP=1 scripts/hardware/run_hardware.sh rx-check 60 A_camN` | 6 × 1 мин |
| **B** | **все шесть, основной режим: 1640×1232, серое, 50 к/с, 15 Мбит/с** | `PTP=1 scripts/hardware/run_hardware.sh rx-check 600 B` | **10 мин** |
| C | то же в цвете | `scripts/hardware/run_hardware.sh configure '{"color":true}'`, затем `PTP=1 … rx-check 300 C` | 5 мин |
| D | 1280×960 серое | `… configure '{"color":false,"width":1280,"height":960}'`, затем `PTP=1 … rx-check 120 D` | 2 мин |
| E | 820×616 серое | `… configure '{"width":820,"height":616}'`, затем `PTP=1 … rx-check 120 E` | 2 мин |
| F | запись: вернуть основной режим, 60 с с движущимся ровером | `… configure '{"width":1640,"height":1232}'`, затем `PTP=1 … rx-record F 60` | 1 мин |
| G | обрыв: во время прогона выдернуть и вернуть кабель camera_3, перезапустить `mocap_camd` на camera_5 | `PTP=1 … rx-check 180 G` | 3 мин |

После F проверьте, что запись читается:

```bash
for f in artifacts/rec_F/*.h264; do ffprobe -v error -count_frames -show_entries stream=width,height,nb_read_frames -of csv=p=0 "$f"; done
wc -l artifacts/rec_F/*.jsonl
```

Число кадров в каждом `.h264` должно совпадать с числом строк в его `.jsonl`.

## 5. Критерии (прогон B; для C–E те же, кроме задержки)

Всё берётся из `artifacts/field_B/rx_summary.json` и вывода `rx_check.txt`:

| Что | Поле | Порог |
|---|---|---|
| частота | `fps` у каждой камеры | 49.5–50.5 |
| потери | `lost` | ≤ 0.1 % кадров (≤ 30 за 10 мин) |
| ошибки распаковки | `decode_fail` | 0 |
| обрывы | `reconnects`, `down_ticks` | 0 |
| задержка | `exp_to_decoded_ms.p50` / `p95` | ≤ 55 / ≤ 65 мс |
| поток | `mbit_s` | около 3–15 на камеру (зависит от сцены) |
| CPU узла | `node_cpu_max` | ≤ 85 % |
| температура узла | `node_temp_max` | < 75 °C |
| PTP | `last_status.ptp.state`, `offset_ns` | SLAVE (camera_1 MASTER), \|смещение\| ≤ 10 000 нс |

Для G: после выдергивания кабеля камера возвращается сама в пределах
нескольких секунд (`reconnects` > 0, остальные камеры без потерь).

**Без PTP** (`PTP=1` не указан) задержка считается по оценке часов
каждого узла, точность ±1 мс. Это допустимо для A, но прогон B делайте с PTP.

## 6. Если что-то не так

- **Камера не стартует**: `journalctl -u mocap_camd -n 30`. «camera busy» —
  работает `camera_node` или другой процесс с камерой.
- **Мало к/с, растёт задержка**: на странице узла смотрите CPU и °C, а в
  `last_status` — `demosaic_ms` и `encoder_ms`. Перегрев в корпусе —
  главный подозреваемый.
- **Потери на отдельных камерах** (как в прошлый раз на camera_2/4/6): при
  такой малой нагрузке их быть не должно. Если есть — запишите, на каких
  камерах, и сделайте перестановку портов и кабелей из
  `docs/field_test_six_cm4_round2.md`, этап 2.
- **PTP не SLAVE**: `journalctl -u ptp4l -n 30`; в `ptp4l` должен быть
  `tx_timestamp_timeout 50`.
